# طرح نمونه‌سازی دستیار نوشتاری کاملاً محلی

**تاریخ:** 2026-11-06  
**وضعیت:** طرح اجرایی نمونه‌سازی؛ هنوز runtime یا مدل به اپ اضافه نشده است.  
**مخزن/شاخه:** H3269/Maseer28-V1 / main

## 1. تصمیم دامنه

از این مرحله به بعد، مأموریت فعال دستیار فقط مکالمه نوشتاری است:
- ورودی و خروجی فقط متن؛
- استنتاج مدل زبانی روی خود دستگاه؛
- عدم ارسال prompt، تاریخچه یا زمینه مکالمه به سرویس هوش مصنوعی ابری؛
- حفظ کنترل‌های ایمنی فعلی و تقدم آن‌ها بر مدل؛
- استفاده از همان پنجره، کادر نوشتار و دکمه ارسال موجود.

ASR، TTS، میکروفون، پخش صدا و هرگونه رابط صوتی از دامنه فعال خارج‌اند. این تصمیم هیچ تغییری در UI ایجاد نمی‌کند. هیچ صفحه، متن، کادر، پنجره، ورودی یا کنترل جدیدی اضافه نخواهد شد.

## 2. حکم امکان‌پذیری فعلی

**حکم: از نظر فنی شدنی، اما هنوز برای ناوگان واقعی تلگرام و بله اثبات نشده و نمی‌توان سازگاری همگانی را وعده داد.**

شواهد:
- Transformers.js اجرای مدل‌های NLP و text generation را در مرورگر، بدون سرور، از طریق ONNX Runtime پشتیبانی می‌کند؛ مسیر پیش‌فرض CPU/WASM و مسیر WebGPU اختیاری است. مستند رسمی استفاده از مدل‌های quantized مانند q4 را برای محیط محدود توصیه می‌کند.
- ONNX Runtime Web، WASM/CPU را در جدول سازگاری برای Chrome Android فهرست می‌کند؛ این سند، سازگاری WebView داخلی Telegram یا Bale را تضمین نمی‌کند.
- مستند ONNX Runtime برای مدل‌های بزرگ محدودیت‌های واقعی ArrayBuffer، حافظه WASM و روش cache کردن مدل را توضیح می‌دهد. بنابراین مدل بزرگ و حافظه آزاد دستگاه، ریسک اصلی است.
- WebLLM به WebGPU وابسته است و برای مسیر پایه همه دستگاه‌ها مناسب فرض نمی‌شود؛ می‌تواند فقط مسیر اختیاری دستگاه‌های واجد شرایط باشد.

## 3. مسیر فنی پیشنهادی برای اثبات

### مسیر پایه مورد آزمون
Transformers.js + ONNX Runtime Web با WASM/CPU و مدل زبانی instruction کوچک و quantized. این صرفاً نامزد prototype است، نه انتخاب نهایی.

### مسیر شتاب‌دار اختیاری
در صورت وجود WebGPU و تأیید عملی در میزبان واقعی، مدل/runtime سازگار با WebGPU سنجیده شود. نبود WebGPU نباید کل دستیار نوشتاری را از کار بیندازد.

### مسیر کم‌منبع
اگر مدل مولد فارسی روی CPU دستگاهی کند، ناپایدار یا بیش از حد پرمصرف باشد، آن دستگاه نباید پاسخ مولدِ ساختگی یا ابری دریافت کند. باید قابلیت محلیِ محدودتر و صادقانه، با همان موتور/دانش فعلی، حفظ شود؛ این fallback به معنی LLM نیست.

## 4. معماری مورد نیاز

1. **Text runtime adapter:** قرارداد مستقل برای load، generate، cancel، dispose و گزارش وضعیت؛ وابستگی مستقیم UI به کتابخانه مدل ممنوع.
2. **Worker isolation:** اجرای inference خارج از thread رابط تا حد امکان؛ توقف و آزادسازی منابع در تغییر صفحه/بسته‌شدن میزبان.
3. **Model lifecycle:** دانلود اولیه صریح و قابل‌فهم با استفاده از کنترل‌های فعلی، اعتبارسنجی فایل، cache پایدار، تشخیص فایل ناقص، پاک‌سازی و بازیابی.
4. **Offline boundary:** پس از دانلود و آماده‌سازی، inference بدون اینترنت؛ هیچ fallback ابری مجاز نیست.
5. **Safety orchestration:** قواعد ایمنی فعلی پیش از inference اجرا شوند؛ مدل حق لغو یا تضعیف handoff/clarification موجود را ندارد. خروجی مدل باید از کنترل‌های خروجی عبور کند.
6. **Context boundary:** ابتدا فقط پیام جاری و زمینه حداقلیِ مجاز؛ اتصال دانش کل اپ و داده‌های شخصی در مرحله مستقل و فقط‌خواندنی. داده حساس پروفایل نباید خودکار به prompt تزریق شود.
7. **Memory:** در این prototype حافظه بلندمدت یا ذخیره transcript اضافه نشود؛ فقط تاریخچه کوتاهِ موقت نشست و با حد مشخص.
8. **No UI expansion:** از textarea، send button، transcript و dialog فعلی استفاده شود. اگر وضعیت بارگیری/خطا/لغو با کنترل‌های فعلی قابل نمایش نباشد، کار متوقف و محدودیت گزارش شود.

## 5. آزمون‌های پذیرش نمونه‌سازی

### آزمون‌های رومیزی
- مدل واقعاً محلی بارگیری و اجرا شود؛ mock یا پاسخ ثابت قابل قبول نیست.
- prompt و history در مسیر inference باقی بمانند و هیچ endpoint ابری فراخوانی نشود.
- پاسخ فارسی، دستورپذیری، حفظ زمینه چندمرحله‌ای، پاسخ به پرسش عمومی، عدم قطعیت و امتناع در نبود دانش ارزیابی شوند.
- آزمون‌های موجود ایمنی و routing بدون افت عبور کنند.
- مدل در Worker اجرا شود و thread رابط هنگام inference قفل نشود.
- قطع شبکه پس از دانلود، اجرای inference را مختل نکند.

### آزمون‌های میدانی
هر میزبان جداگانه: Chrome Android، Telegram Android، Bale Android. در هر میزبان دستگاه کم‌منبع، میان‌رده و پرچم‌دار باید پوشش داده شود. معیارها:
- حجم دانلود و فضای ذخیره؛
- زمان بارگیری اولیه و زمان اولین توکن؛
- سرعت تولید توکن؛
- RAM اوج و crash/reload؛
- پایداری cache پس از بستن/بازکردن میزبان؛
- اجرای کامل در حالت آفلاین؛
- capture شبکه برای اثبات عدم خروج prompt/history/context؛
- رفتار پس‌زمینه، تغییر صفحه، لغو و کمبود حافظه.

آزمون Chrome به‌تنهایی تأیید Telegram یا Bale نیست. دستگاه Samsung SM-A307FN با Android 11 فقط یکی از نمونه‌هاست، نه معیار کل ناوگان.

## 6. دروازه تصمیم

نمونه‌سازی فقط وقتی موفق تلقی می‌شود که:
- inference واقعی و فارسی روی دستگاه انجام شود؛
- حداقل یک مسیر WASM/CPU و هر مسیر شتاب‌دارِ ادعاشده جداگانه اندازه‌گیری شود؛
- هیچ داده مکالمه به AI ابری ارسال نشود؛
- معیارهای RAM/سرعت/پایداری برای هر میزبان و طبقه دستگاه ثبت شوند؛
- آزمون ایمنی موجود بدون regression عبور کند.

اگر مدل روی دستگاه کم‌منبع قابل‌قبول نباشد، دامنه سخت‌افزاری پنهانی محدود نمی‌شود؛ محدودیت همان ترکیب دستگاه/میزبان مستند و fallback صادقانه تعریف می‌شود.

## 8. مواردی که هنوز اثبات نشده‌اند

- مدل فارسی مشخص و مجوز استفاده تجاری/توزیع آن؛
- کیفیت مکالمه طبیعی فارسی در برابر مجموعه ارزیابی مستقل؛
- سرعت و RAM در دستگاه‌های واقعی؛
- کارکرد runtime در WebView تلگرام و بله؛
- ماندگاری cache مدل و اجرای آفلاین در هر دو میزبان؛
- امکان انجام همه حالت‌های بارگیری/خطا با UI موجود.

تا پیش از عبور از این موارد، هیچ مدل یا runtime به محصول اضافه و هیچ قابلیت LLM محلی آماده اعلام نمی‌شود.

## 9. نامزد فارسی مشخص برای prototype — IbnSina + wllama (2026-11-06)

بررسی تکمیلی منابع فنی، یک مسیر مناسب‌تر از گزینه عمومی Transformers.js برای آزمون اول نشان داد:
- **Runtime نامزد:** `@wllama/wllama`؛ binding مبتنی بر llama.cpp برای اجرای GGUF در مرورگر با WebAssembly و بدون الزام WebGPU؛ WebGPU در صورت وجود فقط شتاب‌دهنده اختیاری است.
- **مدل نامزد:** `ibnsina-llm/ibnsina-1.5b`، فایل `ibnsina-1.5b-Q4_K_M.gguf` با اندازه اعلام‌شده حدود 904 MB و مجوز Apache-2.0.
- مدل فارسی‌محور و instruction-tuned است؛ chat template در GGUF موجود است و context اعلام‌شده 2048 token است.

### محدودیت تعیین‌کننده مدل
سازنده صریحاً اعلام کرده مدل برای نوشتن/خلاصه/ترجمه/گفت‌وگوی فارسی است، نه پاسخ به پرسش دانشی یا مشاوره؛ همچنین احتمال تولید جمله روان اما نادرست وجود دارد. بنابراین این مدل نباید منبع دانش یا مرجع راهنمایی روان‌شناختی تلقی شود. در صورت موفقیت فنی، فقط می‌تواند نامزد لایه زبان/گفت‌وگوی عمومی باشد و هر محتوای تخصصی باید از دانش تأییدشده و سیاست‌های فعلی عبور کند. هیچ داده یا محتوای حساس نباید بدون قرارداد و کنترل مجاز به prompt افزوده شود.

### ریسک‌های اجرایی
- دانلود اولیه حدود 904 MB برای بسیاری از کاربران سنگین است؛ امکان resume، cache پایدار، فضای آزاد و حذف مدل باید آزمایش شود.
- حافظه واقعی حین inference از اندازه فایل بیشتر است؛ RAM گوشی مالک 4GB است اما این عدد به‌تنهایی قبولی را ثابت نمی‌کند.
- WASM روی موبایل ممکن است کند باشد؛ wllama خودش WebAssembly SIMD و محدودیت‌های سازگاری مرورگر را مطرح می‌کند. عملکرد در WebView تلگرام و بله ناشناخته است.
- مدل context کوتاه 2048 token دارد؛ باید تاریخچه و زمینه به‌صورت سخت‌گیرانه محدود و خلاصه شوند.
- مجوز Apache-2.0 مدل باید همراه وزن‌ها و attribution لازم حفظ شود.

### تصمیم نمونه‌سازی
این ترکیب به‌عنوان **اولین نامزد قابل‌آزمایش** ثبت می‌شود، نه انتخاب محصول. پیش از افزودن dependency یا مدل به اپ باید یک spike ایزوله، inference واقعی با داده ساختگی، تست chat template، بررسی حافظه و بررسی رفتار Worker انجام شود. سپس با همان رابط موجود و بدون افزودن UI، آزمون میزبان واقعی انجام می‌شود. گزینه Transformers.js/ONNX همچنان مسیر مقایسه‌ای جایگزین است.

منابع:
- wllama: https://github.com/ngxson/wllama
- IbnSina 1.5B model card: https://huggingface.co/ibnsina-llm/ibnsina-1.5b

### نکته تکمیلی سازگاری wllama و محدودیت کاربرد مدل
- مستند wllama می‌گوید inference در Worker انجام می‌شود و WASM SIMD برای اجرای بدون GPU دارد؛ اما اجرای چندریسمانی به هدرهای COOP و COEP نیاز دارد. وجود/امکان تنظیم این هدرها در هر سه میزبان باید جداگانه بررسی شود. در نبود آن، مسیر تک‌ریسمانی باید benchmark شود؛ نباید multi-thread را مفروض گرفت.
- wllama برای دانلود سریع‌تر و کاهش خطای حافظه، تقسیم مدل به قطعات حداکثر 512 MB را توصیه می‌کند؛ مدل 904 MB نامزد باید پیش از استفاده در مینی‌اپ به‌صورت قطعه‌ای آماده شود یا مسیر دانلودی معادل و قابل اعتماد داشته باشد.
- مدل‌کارت ابن‌سینا کاربرد روزمره را ذکر می‌کند، اما برای تصمیم‌های پزشکی/حقوقی/مالی مناسب نمی‌داند و دقت آن در آزمون‌های دانشی فارسی محدود است؛ در ارزیابی PersianMedQA نتیجه 26.8% در برابر خط پایه تصادفی 25% گزارش شده است. بنابراین در محصول روان‌شناختی، این مدل نباید توصیه بالینی، تشخیص، راهکار درمانی یا ادعای علمی تولید کند. حداکثر نقش قابل بررسی آن، کمک به فهم و صورت‌بندی گفت‌وگوی عمومی/غیرتخصصی است؛ هر پاسخ تخصصی باید از منبع تأییدشده و منطق کنترل‌شده عبور کند.



## 10. بازبینی نسخه واقعی wllama و مسیر سازگاری مرورگر (2026-11-06)

بازبینی دوباره مخزن upstream و صفحه انتشار npm یک نکته مهم را روشن کرد که باید پیش از هر نصب dependency رعایت شود:

- صفحه npm در زمان بررسی نسخه منتشرشده `@wllama/wllama` را `3.8.1` نشان می‌دهد؛ فایل `package.json` شاخه master مخزن upstream نسخه توسعه‌ای `3.12.0` را نشان می‌دهد. این دو را نباید یکی فرض کرد. برای prototype باید فقط نسخه منتشرشده و دقیق npm pin شود؛ استفاده از master یا نسخه فرضی ممنوع است.
- نسل جدید runtime به قابلیت‌های WebAssembly JSPI و MEMORY64 متکی است. بسته اختیاری `@wllama/wllama-compat` برای مرورگرهایی که این قابلیت‌ها را ندارند، build سازگار مبتنی بر Asyncify و wasm32 فراهم می‌کند؛ این مسیر کندتر است و محدودیت حافظه متفاوت دارد.
- رفتار پیش‌فرض compat در صورت نیاز، دریافت asset از jsDelivr است. برای رعایت سیاست عدم وابستگی اجرایی به CDN و قابل‌ممیزی بودن کد، اگر wllama انتخاب شد باید فایل‌های compat در build خود محصول self-host شوند و ارجاع CDN غیرفعال/حذف شود. دریافت runtime از CDN در زمان اجرا پذیرفته نیست.
- multi-thread همچنان به COOP/COEP و SharedArrayBuffer وابسته است. چون نمی‌توان فرض کرد Telegram/Bale این headerها را ارائه می‌کنند، مسیر تک‌ریسمانی WASM باید مستقل benchmark شود و multi-thread فقط قابلیت اختیاری پس از feature-detection باشد.
- بنابراین صرف پشتیبانی Chrome 156 به معنی پشتیبانی WebView داخلی Telegram 13.1.1 یا Bale 10.05.08 نیست؛ قابلیت‌های JSPI، MEMORY64، WASM SIMD، Worker، storage و رفتار compat باید در هر میزبان جداگانه سنجیده شوند.

### مقایسه مدل برای آزمون منابع
- IbnSina 1.5B Q4_K_M با حجم حدود 904 MB فارسی‌محور است، اما خود model card صریحاً آن را برای نوشتن/خلاصه/ترجمه/گفت‌وگوی فارسی می‌داند و برای مشاوره یا پرسش دانشی توصیه نمی‌کند؛ نتایج منتشرشده آن در PersianMedQA برابر 26.8% در برابر خط پایه تصادفی 25% گزارش شده است. این مدل نباید مرجع علمی یا درمانی دستیار باشد.
- Qwen2.5 0.5B Instruct Q4_K_M با حجم حدود 491 MB یک نامزد کوچک‌تر برای سنجش فشار حافظه/سرعت است، اما فارسی‌فهمی و کیفیت مکالمه آن برای نیاز این اپ هنوز benchmark نشده است؛ کوچک‌تر بودن به معنی مناسب‌تر بودن نیست.
- هر دو فقط نامزد آزمون‌اند. معیار انتخاب، ارزیابی فارسی مستقل، رعایت ایمنی، سرعت/RAM، اندازه دانلود و سازگاری میزبان است؛ نه صرفاً حجم فایل یا ادعای model card.

### تصمیم اجرایی اصلاح‌شده
1. پیش از نصب در اپ، نسخه دقیق npm و فایل‌های runtime/compat باید pin و از نظر مجوز، integrity، حجم و مسیر asset بررسی شوند.
2. نخستین prototype باید فقط یک آزمون ایزوله runtime با داده ساختگی باشد؛ هیچ prompt یا تاریخچه واقعی کاربر به آن داده نشود.
3. در مرحله اول هیچ تغییر در `GlobalAssistantLauncher`، `pageAssistantTurn`، موتور ایمنی یا UI انجام نشود.
4. اگر runtime در یک میزبان نیازمند CDN خارجی، header غیرقابل‌تأمین یا API غیرقابل‌دسترسی باشد، آن مسیر برای همان میزبان رد می‌شود؛ به fallback ابری تبدیل نمی‌شود.
