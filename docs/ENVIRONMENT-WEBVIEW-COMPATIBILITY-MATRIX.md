## 2. تفاوت‌های عمدی Test و Production

### پرچم‌ها
در `src/features/journey/journeyStore.js` پیکربندی شاخه main به شکل زیر ثبت شده است:

```js
export const APP_CONFIG = {
  TEST_MODE: true,
  TIME_LOCK_ENABLED: false,
  TIME_ZONE: 'Asia/Tehran',
};
```

اسکریپت `scripts/prepare-production-build.mjs` در ساخت production این دو مقدار را به `false` و `true` تغییر می‌دهد.

### اثر رفتاری
- آرشیو مسیر ناقص: در حالت آزمایش مجاز است؛ در production فقط مسیر کامل باید آرشیو شود. محل بررسی: `src/App.jsx`، شرط `shouldArchiveCurrentPath`.
- دستیار آزمایشی: در TEST_MODE روشن است؛ در production به‌طور پیش‌فرض پنهان می‌شود، مگر `VITE_ENABLE_EXPERIMENTAL_ASSISTANT=true` تنظیم شود. محل: `src/features/journey/JourneyScreens.jsx`.
- قفل روزانه: در main خاموش است تا آزمون مسیرها آسان باشد؛ در production روشن است و منطق زمان معتبر/منطقه زمانی تهران اعمال می‌شود.
- مسیر پایه Vite: `/Maseer28-V1/` برای مخزن آزمایش و `/Maseer28/` برای مخزن مقصد production است. محل: `vite.config.js`.

**قاعده نگهداری:** این تفاوت‌ها را برای یکسان‌سازی ظاهری حذف نکنید. هر تغییر در این پرچم‌ها باید همراه آزمون مستقل test build و production build باشد.

## 3. Bale و Telegram: آنچه کد واقعاً ثابت می‌کند

### Bale
- `src/main.jsx` در User-Agent به دنبال `bale` می‌گردد و کلاس `bale-webview` را روی صفحه قرار می‌دهد.
- `src/features/library/Reader.jsx` برای عرض کتاب‌خوان در Bale رفتار اختصاصی دارد.
- `src/styles/original-v72.css` قواعد ظاهری اختصاصی برای header، bottom navigation و فاصله‌گذاری Bale دارد.

این موارد، سازگاری ظاهری/چیدمان‌اند؛ شواهدی از دو موتور مستقل مسیر یا محتوای متفاوت نیستند.

### Telegram
- در بررسی کد، اتصال مستقیم و صریح به `window.Telegram.WebApp` مشاهده نشد.
- این موضوع به معنی تضمین سازگاری کامل نیست؛ اپ عمدتاً از APIهای معمول مرورگر استفاده می‌کند و WebView میزبان می‌تواند در فایل، دانلود، پنجره و schemeهای خارجی رفتار متفاوتی داشته باشد.

### نتیجه انتشار
کد موجود، bundle مشترک با تشخیص User-Agent بله را نشان می‌دهد. از شواهد بررسی‌شده نمی‌توان نتیجه گرفت که artifact زنده Bale دقیقاً همان artifact زنده Telegram است یا فرایند انتشار جداگانه‌ای ندارد. این موضوع باید از تنظیمات واقعی کانال انتشار و نسخه نصب‌شده تأیید شود.

## 4. قابلیت‌های خروجی و فایل: وضعیت شواهد

| قابلیت/مسیر | وضعیت کد | ریسک میزبان WebView | نتیجه فعلی |
|---|---|---|---|
| ZIP شامل PDF آرشیوها | دکمه صفحه Archive تابع `exportArchivesZip` را اجرا و `triggerBlobDownload` را فراخوانی می‌کند؛ هر آرشیو یک PDF تصویری داخل ZIP می‌سازد | Canvas/JPEG/PDF، دانلود، ذخیره و بازکردن ZIP باید در هر میزبان جداگانه آزموده شود | مسیر UI در `main` متصل است؛ CI/Chromium موفق، Android/Telegram/Bale هنوز تأییدنشده |

| بازیابی JSON | file input و `file.text()` | بازشدن picker و تحویل فایل ممکن است بین WebViewها متفاوت باشد | فعال در کد؛ نیازمند آزمون واقعی |
| helper عمومی `downloadJson` | در `src/shared/utils.js` تعریف شده؛ ارجاع مصرفی پیدا نشد | فعلاً مسیر کاربر نیست | نامزد کد بلااستفاده؛ بدون تصمیم مالک حذف نشود |
| SMS | scheme `sms:` و bridgeهای اختیاری Android/WebKit | bridgeها در Telegram/Bale تضمین‌شده نیستند؛ scheme به میزبان/سیستم‌عامل وابسته است | نیازمند آزمون روی دستگاه |
| Clipboard | `copyTextToClipboard` ابتدا Clipboard API و سپس fallback کنترل‌شده را اجرا می‌کند؛ false/throw به‌عنوان موفقیت گزارش نمی‌شود | مجوزها و paste واقعی در هر WebView باید آزموده شود | تست واحد fallback و شکست موفق؛ پذیرش میزبان هنوز لازم است |
| لینک خارجی و پنجره جدید | `window.open` و `target="_blank"` در مسیرهای مختلف | ممکن است درون WebView باز شود، به مرورگر منتقل شود یا مسدود شود | نیازمند آزمون میزبان |
| `window.print` و `navigator.share` | استفاده فعال در جست‌وجوی انجام‌شده پیدا نشد | — | فعلاً مبنای تصمیم نیست |

### نکته مهم ZIP/PDF
در نسخه فعلی `main`، صفحه Archive دکمه «دریافت خروجی ZIP و PDF آرشیوها» دارد: برای هر آرشیو یک PDF تصویری روی Canvas ساخته و همه PDFها در یک ZIP بدون فشرده‌سازی (store) قرار می‌گیرند؛ سپس دانلود با Blob URL درخواست می‌شود. فایل PDF مستقل جداگانه دانلود نمی‌شود. پیام UI فقط dispatch درخواست دانلود را اعلام می‌کند و ذخیره واقعی فایل را تضمین نمی‌کند. PDFها raster هستند و متن قابل جست‌وجو/انتخاب نیست. تست واحد ساختار ZIP/PDF و آزمون Chromium دانلود واقعی مرورگر موفق‌اند؛ این شواهد سازگاری Android WebView میزبان را ثابت نمی‌کنند. ZIP/PDF شامل پاسخ‌ها و بازخوردهای مسیر است و همچنان می‌تواند داده روان‌شناختی حساس باشد؛ فیلدهای پروفایل مستقل نباید در آن حضور داشته باشند.

### تفاوت API رسمی میزبان‌ها
- **Telegram:** از Bot API 8.0 متد `Telegram.WebApp.downloadFile` وجود دارد، اما پارامتر آن یک URL از نوع HTTPS و نام فایل است. مستندات برای رفتار پایدار، پاسخ `Content-Disposition: attachment` و در وب `Access-Control-Allow-Origin: https://web.telegram.org` را توصیه می‌کنند. خروجی فعلی به‌صورت Blob محلی ساخته می‌شود و URL آن `blob:` است؛ بنابراین مستقیماً با قرارداد HTTPS متد رسمی سازگار نیست. در مخزن فعلی endpoint سمت سرور برای میزبانی موقت فایل پیدا نشد. منبع: https://core.telegram.org/bots/webapps#downloadfileparams
- **Bale:** مستندات رسمی فعلی `Bale.WebApp` متدهایی مانند `openLink` را فهرست می‌کنند، اما متد بومی `downloadFile` در فهرست فعلی مستند نشده است. این نبود مستندات، شکست قطعی دانلود HTML را ثابت نمی‌کند؛ فقط یعنی نمی‌توان به API بومی دانلود اتکا کرد. منبع: https://docs.bale.ai/miniapp
- **نتیجه فنی:** `triggerBlobDownload` فعلاً فقط دانلود استاندارد مرورگر با لینک Blob را درخواست می‌کند. Chromium آن را ذخیره کرده، اما این آزمون نه پذیرش فایل در Telegram را ثابت می‌کند و نه در Bale. تا آزمون دستگاه واقعی، وضعیت هر دو میزبان «تأییدنشده» باقی می‌ماند؛ مسیر را نه موفق اعلام می‌کنیم و نه بدون آزمون، ناممکن.


## 5. رفتار آرشیو در نسخه فعلی main

تغییرات P3 در commit `a406cacbf8205d70812edc65ebf65fac4fb06684` وارد `main` شده‌اند؛ بنابراین معیارهای زیر اکنون رفتار مورد انتظار محیط تست هستند:
- سقف عملیاتی آرشیو ۲۰ مسیر است؛ رکوردهای قدیمی بیش از سقف هنگام بارگذاری بی‌صدا حذف نمی‌شوند.
- در ظرفیت کامل، شروع مسیر تازه متوقف می‌شود تا کاربر یک آرشیو مشخص را حذف کند.
- حذف انتخابی فقط همان آرشیو را حذف می‌کند و مسیر فعال/سایر آرشیوها را دست‌نخورده می‌گذارد.
- در شکست نوشتن یا راستی‌آزمایی، پیام موفقیت نباید نشان داده شود و امکان تلاش مجدد باید حفظ شود.

این رفتار در آزمون‌های واحد و سناریوهای Chromium بررسی شده است؛ پذیرش WebView واقعی Telegram و Bale هنوز باز است.

## 8. تصمیم‌های باز محصول

1. خروجی ZIP شامل PDFهای تصویری اکنون در UI شاخه P3 متصل است؛ باید در Chrome Android، Telegram و Bale از نظر دانلود، استخراج ZIP و خوانایی PDF پذیرفته شود.
2. آیا helper بلااستفاده `downloadJson` پس از یک جست‌وجوی مصرف کامل حذف شود؟
3. آیا خروجی JSON و بازیابی آن در هر دو WebView جزو قابلیت‌های پشتیبانی‌شده رسمی هستند؟
4. سیاست نگهداری آرشیوها و حذف داده‌ها چیست؟ حذف از localStorage/IndexedDB، فایل export دانلودشده را از دستگاه کاربر پاک نمی‌کند.

اتصال ZIP/PDF اکنون در main و محیط تست انسانی فعال است؛ قبولی آن در Telegram و Bale فقط پس از آزمون واقعی دستگاه اعلام می‌شود. helperهای بلااستفاده را بدون جست‌وجوی مصرف کامل حذف نکنید.
