# ماتریس تفاوت محیط آزمایش، انتشار و سازگاری WebView

> وضعیت: ممیزی ایستا بر پایه کد مخزن؛ آزمون میدانی Android WebView در Telegram و Bale هنوز انجام نشده است.
> تاریخ ثبت: 2026-11-03
> دامنه: مخزن `H3269/Maseer28-V1`، شاخه `main` و شاخه کاری `p3/controlled-restore-executor`.

## 1. قواعدی که نباید با هم اشتباه شوند

| لایه | محیط/نسخه | معنی |
|---|---|---|
| آزمایش توسعه | V1 `main` | محیط مرجع آزمایش؛ `TEST_MODE=true` و `TIME_LOCK_ENABLED=false` |
| ساخت انتشار | خروجی اسکریپت production | در زمان build مقدارهای `TEST_MODE=false` و `TIME_LOCK_ENABLED=true` جایگزین می‌شوند |
| نسخه مقصد | مخزن `H3269/Maseer28` | artifact منتشرشده؛ لزوماً هم‌سطح آخرین main نیست |

| P3 | `p3/controlled-restore-executor` | شاخه کاری تغییرات حریم خصوصی/بازیابی؛ هنوز با main یکی نیست و PR آن نباید merge فرض شود |

## 2. تفاوت‌های عمدی Test و Production

### پرچم‌ها
در `src/features/journey/journeyStore.js` پیکربندی شاخه main به شکل زیر ثبت شده است:

```js
export const APP_CONFIG = {
  TEST_MODE: true,
  TIME_LOCK_ENABLED: false,
  TIME_ZONE: 'Asia/Tehran',
};
```

اسکریپت `scripts/prepare-production-build.mjs` در ساخت production این دو مقدار را به `false` و `true` تغییر می‌دهد.

### اثر رفتاری
- آرشیو مسیر ناقص: در حالت آزمایش مجاز است؛ در production فقط مسیر کامل باید آرشیو شود. محل بررسی: `src/App.jsx`، شرط `shouldArchiveCurrentPath`.
- دستیار آزمایشی: در TEST_MODE روشن است؛ در production به‌طور پیش‌فرض پنهان می‌شود، مگر `VITE_ENABLE_EXPERIMENTAL_ASSISTANT=true` تنظیم شود. محل: `src/features/journey/JourneyScreens.jsx`.
- قفل روزانه: در main خاموش است تا آزمون مسیرها آسان باشد؛ در production روشن است و منطق زمان معتبر/منطقه زمانی تهران اعمال می‌شود.
- مسیر پایه Vite: `/Maseer28-V1/` برای مخزن آزمایش و `/Maseer28/` برای مخزن مقصد production است. محل: `vite.config.js`.

**قاعده نگهداری:** این تفاوت‌ها را برای یکسان‌سازی ظاهری حذف نکنید. هر تغییر در این پرچم‌ها باید همراه آزمون مستقل test build و production build باشد.

## 3. Bale و Telegram: آنچه کد واقعاً ثابت می‌کند

### Bale
- `src/main.jsx` در User-Agent به دنبال `bale` می‌گردد و کلاس `bale-webview` را روی صفحه قرار می‌دهد.
- `src/features/library/Reader.jsx` برای عرض کتاب‌خوان در Bale رفتار اختصاصی دارد.
- `src/styles/original-v72.css` قواعد ظاهری اختصاصی برای header، bottom navigation و فاصله‌گذاری Bale دارد.

این موارد، سازگاری ظاهری/چیدمان‌اند؛ شواهدی از دو موتور مستقل مسیر یا محتوای متفاوت نیستند.

### Telegram
- در بررسی کد، اتصال مستقیم و صریح به `window.Telegram.WebApp` مشاهده نشد.
- این موضوع به معنی تضمین سازگاری کامل نیست؛ اپ عمدتاً از APIهای معمول مرورگر استفاده می‌کند و WebView میزبان می‌تواند در فایل، دانلود، پنجره و schemeهای خارجی رفتار متفاوتی داشته باشد.

### نتیجه انتشار
کد موجود، bundle مشترک با تشخیص User-Agent بله را نشان می‌دهد. از شواهد بررسی‌شده نمی‌توان نتیجه گرفت که artifact زنده Bale دقیقاً همان artifact زنده Telegram است یا فرایند انتشار جداگانه‌ای ندارد. این موضوع باید از تنظیمات واقعی کانال انتشار و نسخه نصب‌شده تأیید شود.

## 4. قابلیت‌های خروجی و فایل: وضعیت شواهد

| قابلیت/مسیر | وضعیت کد | ریسک میزبان WebView | نتیجه فعلی |
|---|---|---|---|
| ZIP شامل PDF آرشیوها | `src/features/journey/archiveExport.js` وجود دارد؛ `exportArchivesZip` یک Blob برمی‌گرداند | تولید Canvas/JPEG/PDF و دانلود فایل باید در WebView آزموده شود | در صفحه Archive اتصال/دکمه‌ای پیدا نشد؛ قابلیت فعال UI اثبات نشده |
| خروجی JSON پشتیبانی | مسیر فعال با Blob، `URL.createObjectURL` و لینک `download` | دانلود و ذخیره فایل در Telegram و Bale نیازمند آزمون واقعی است | فعال در کد؛ شکست در WebView اثبات نشده |
| بازیابی JSON | file input و `file.text()` | بازشدن picker و تحویل فایل ممکن است بین WebViewها متفاوت باشد | فعال در کد؛ نیازمند آزمون واقعی |
| helper عمومی `downloadJson` | در `src/shared/utils.js` تعریف شده؛ ارجاع مصرفی پیدا نشد | فعلاً مسیر کاربر نیست | نامزد کد بلااستفاده؛ بدون تصمیم مالک حذف نشود |
| SMS | scheme `sms:` و bridgeهای اختیاری Android/WebKit | bridgeها در Telegram/Bale تضمین‌شده نیستند؛ scheme به میزبان/سیستم‌عامل وابسته است | نیازمند آزمون روی دستگاه |
| Clipboard | `legacyCopy` از `document.execCommand('copy')` استفاده می‌کند و نتیجه را به‌درستی کنترل نمی‌کند | مجوزها/رفتار WebView ممکن است متفاوت باشد | ریسک صحت بازخورد موفقیت؛ باید اصلاح یا آزموده شود |
| لینک خارجی و پنجره جدید | `window.open` و `target="_blank"` در مسیرهای مختلف | ممکن است درون WebView باز شود، به مرورگر منتقل شود یا مسدود شود | نیازمند آزمون میزبان |
| `window.print` و `navigator.share` | استفاده فعال در جست‌وجوی انجام‌شده پیدا نشد | — | فعلاً مبنای تصمیم نیست |

### نکته مهم ZIP/PDF
کد `archiveExport.js` خودش دانلود را trigger نمی‌کند؛ فقط Blob برمی‌گرداند. همچنین در بررسی صفحه آرشیو، call-site یا دکمه‌ای که این تابع را اجرا کند پیدا نشد. بنابراین فعلاً نباید به کاربر گفته شود «خروجی ZIP/PDF در Telegram/Bale کار نمی‌کند»؛ گزاره دقیق این است: «کد تولید خروجی وجود دارد، اما مسیر کاربری متصل و قابل استفاده در نسخه بررسی‌شده اثبات نشده است.»

## 5. تفاوت منطق آرشیو main و شاخه P3

این تفاوت، تفاوت Telegram و Bale نیست؛ تفاوت دو شاخه Git است.

### main (مبنای آزمایش فعلی)
- sanitize آرشیو در مسیر مورد بررسی از `.slice(0,20)` استفاده می‌کند؛ ممکن است رکوردهای قدیمی‌تر بدون انتخاب صریح کاربر از داده نگهداری‌شده خارج شوند.
- منطق قدیمی آستانه ۱۲ مسیر و پاک‌سازی آرشیو/مسیر فعال در main وجود دارد.
- این منطق‌ها با اسکریپت production به‌عنوان پرچم محیطی جایگزین نمی‌شوند؛ بنابراین نباید فرض کرد فقط در تست رخ می‌دهند.

### P3 (شاخه کاری، هنوز ادغام‌نشده)
- سقف آرشیو ۲۰ مسیر است.
- sanitize آرشیو legacy را با کوتاه‌سازی بی‌صدا حذف نمی‌کند.
- در ظرفیت کامل، شروع مسیر جدید متوقف می‌شود تا کاربر یک آرشیو مشخص را انتخاب و حذف کند.
- حذف انتخابی جایگزین حذف دسته‌جمعی شده است.
- شکست حذف نباید dialog را ببندد یا موفقیت کاذب نشان دهد.

**قاعده نگهداری:** تا زمان ادغام و انتشار تأییدشده P3، رفتار P3 را به main یا نسخه live نسبت ندهید. هر باگ آرشیو باید با ذکر SHA و شاخه‌ای که از آن گزارش شده ثبت شود.

## 6. چک‌لیست پذیرش دستی Telegram و Bale

هر دو برنامه باید جداگانه روی دستگاه Android واقعی بررسی شوند. اجرای Chrome دسکتاپ یا شبیه‌ساز به‌تنهایی جای این آزمون را نمی‌گیرد.

| شناسه | آزمون | شواهد لازم |
|---|---|---|
| WV-01 | بازشدن اپ، refresh و بازگشت از پس‌زمینه | ویدئو/گزارش نسخه و دستگاه |
| WV-02 | پیمایش، header و bottom navigation | ثبت رفتار در هر دو میزبان |
| WV-03 | خروجی JSON | فایل واقعاً ذخیره شود و JSON معتبر باشد |
| WV-04 | بازیابی JSON | انتخاب فایل، preview/اعتبارسنجی و نتیجه بازیابی |
| WV-05 | Clipboard | متن در برنامه مقصد واقعاً paste شود؛ پیام موفقیت کاذب نباشد |
| WV-06 | SMS | بازشدن برنامه پیامک با گیرنده/متن مورد انتظار |
| WV-07 | لینک خارجی و `target=_blank` | مقصد و روش بازشدن ثبت شود |
| WV-08 | کتاب‌خوان و اسکرول | عرض، برش متن، اسکرول و چیدمان |
| WV-09 | قفل روزانه در build production | زمان معتبر، منطقه تهران و fail-closed در خطای زمان |

برای هر نتیجه باید این اطلاعات ثبت شود: نام میزبان و نسخه آن، نسخه Android، مدل دستگاه، URL/commit یا شناسه build، تاریخ آزمون، مراحل بازتولید، نتیجه و فایل شاهد. بدون این داده‌ها، برچسب «در تلگرام خراب است» یا «در بله کار نمی‌کند» قابل دفاع نیست.

## 8. تصمیم‌های باز محصول

1. آیا خروجی ZIP/PDF باید واقعاً به رابط آرشیو اضافه شود یا کد بلااستفاده آن در cleanup آینده حذف شود؟
2. آیا helper بلااستفاده `downloadJson` پس از یک جست‌وجوی مصرف کامل حذف شود؟
3. آیا خروجی JSON و بازیابی آن در هر دو WebView جزو قابلیت‌های پشتیبانی‌شده رسمی هستند؟
4. سیاست نگهداری آرشیوها و حذف داده‌ها چیست؟ حذف از localStorage/IndexedDB، فایل export دانلودشده را از دستگاه کاربر پاک نمی‌کند.

تا دریافت تصمیم روشن، هیچ‌یک از قابلیت‌های نام‌برده حذف یا به UI متصل نمی‌شود.
