# موجودی داده و معماری حریم خصوصی مسیر۲۸

**تاریخ:** 2026-11-01  
**مبنای بررسی:** کد `journeyStore.js`، `JourneyScreens.jsx`، `App.jsx`، مخزن کتابخانه IndexedDB و جست‌وجوی استاتیک مخزن  
**وضعیت:** موجودی اولیه داده و تحلیل ریسک؛ نه ممیزی کامل شبکه/مرورگر یا ارزیابی حقوقی

## ۱. یافته اصلی

اپلیکیشن فعلی یک برنامه وب سمت‌کاربر است و داده‌های اصلی مسیر در مرورگر ذخیره می‌شوند. در کد بررسی‌شده، شواهدی از ارسال متن آزاد روزانه، اطلاعات پروفایل یا پاسخ‌های ارزیابی به یک API هوش مصنوعی یا backend اختصاصی پیدا نشد. این به معنی اثبات نبود سرویس‌های میزبانی، لاگ‌های CDN، تحلیل‌گرهای احتمالی یا سرویس‌های خارج از مخزن نیست.

**نتیجه معماری:** افزودن دستیار ابری یا همگام‌سازی، یک تغییر کوچک UI نیست؛ این کار مرز پردازش داده را از دستگاه کاربر به یک پردازشگر بیرونی تغییر می‌دهد و باید بعد از تصمیم رسمی حریم خصوصی و طراحی backend انجام شود.

## ۲. موجودی داده‌های شناسایی‌پذیر و حساس

| داده | محل ذخیره فعلی | حساسیت/ریسک | اقدام پیشنهادی |
|---|---|---|---|
| نام | `maseer28_state` و `maseer28_user_profile_v1` | شناسایی مستقیم | حذف از داده ارسالی به AI؛ استفاده از شناسه تصادفی جلسه |
| سن | همان دو کلید | داده شخصی؛ برای افراد زیر ۱۸ سال ملاحظات ویژه | جمع‌آوری فقط در صورت نیاز مستند؛ سیاست سنی مستقل |
| جنسیت | همان دو کلید | داده شخصی حساس در برخی نظام‌های حقوقی | اختیاری‌کردن یا حذف اگر کاربرد روشن ندارد |
| شماره تماس | همان دو کلید | شناسه تماس مستقیم | حذف از پروفایل پیش‌فرض مگر کاربرد عملیاتی و رضایت روشن |
| وضعیت پزشکی و یادداشت پزشکی | همان دو کلید | داده سلامت بسیار حساس | حذف از ذخیره پیش‌فرض؛ در صورت ضرورت، کمینه‌سازی و رضایت جداگانه |
| وضعیت دارو و ریسک دارو | همان دو کلید | داده سلامت/دارویی حساس | عدم جمع‌آوری مگر نیاز ایمنی روشن و بررسی متخصص |
| موضوع مسیر، مدت و هدف | `maseer28_state` و آرشیو | ممکن است اطلاعات روان‌شناختی و زندگی خصوصی آشکار کند | طبقه‌بندی به‌عنوان داده حساس؛ retention محدود |
| پاسخ‌های روزانه و متن بازخورد | `answers` و `daily` در state | احتمال افشای آسیب، رابطه، سلامت و خودآسیبی | حساس‌ترین محتوای کاربر؛ ذخیره و ارسال فقط با کنترل صریح |
| پاسخ‌های ارزیابی آغاز/پایان و نمره | `assessmentData` و `final` | داده سلامت روان/خودارزیابی | برچسب‌گذاری به‌عنوان self-report غیرتشخیصی؛ retention محدود |
| گزارش نهایی آزاد | فیلدهای `f1` تا `f4` در `final` | متن آزاد با احتمال اطلاعات بسیار حساس | حذف/ناشناس‌سازی هنگام export و حذف کامل با درخواست کاربر |
| مسیرهای آرشیوشده | `archive` در state، تا ۲۰ رکورد | تکرار داده‌های پروفایل و پاسخ‌های حساس گذشته | نمایش تعداد، حذف مستقل و سیاست انقضا |
| کد مسیر و زمان‌ها | `pathId`, `startedAt`, guardهای زمان | ریسک کمتر؛ امکان پیوند دادن رویدادها | فقط به اندازه نیاز نگهداری شود |

## ۳. محل ذخیره‌سازی مشاهده‌شده

### localStorage
کلیدهای اصلی:
- `maseer28_state`: وضعیت مسیر، پروفایل، پاسخ‌ها، داده ارزیابی، بازخوردها، نتیجه نهایی و آرشیو.
- `maseer28_user_profile_v1`: نسخه جداگانه‌ای از پروفایل شامل نام، سن، جنسیت، شماره تماس و فیلدهای پزشکی/دارویی.
- `maseer28_onboarding_complete_v1`: وضعیت تکمیل onboarding.
- `maseer28_trusted_clock_guard_v2` و `maseer28_start_guard_v2`: داده‌های محافظ ساعت/شروع مسیر.
- کلیدهای پذیرش حق نشر و سایر تنظیمات.

پروفایل در دو محل تکرار می‌شود؛ این موضوع دامنه حذف، اصلاح و migration را پیچیده می‌کند. حذف آرشیو فعلی از طریق `clearArchiveAndCurrentPath`، پروفایل مستقل را پاک نمی‌کند.

### IndexedDB
پایگاه `maseer28-library` شامل کتاب‌ها، نسخه‌های کتاب و تنظیمات seed است. محتوای کتابخانه در این بررسی، داده عمومی محتوایی است؛ اما باید پیش از هرگونه ذخیره یادداشت یا annotation کاربر، طبقه‌بندی مجدد شود.

## ۴. تهدیدها و محدودیت‌ها

1. localStorage و IndexedDB رمزنگاری اختصاصی سمت برنامه ندارند. داده‌ها در دستگاه کاربر باقی می‌مانند، اما کد مخرب same-origin یا XSS می‌تواند به آن‌ها دسترسی پیدا کند.
2. کنترل دسترسی در سطح دستگاه/مرورگر جایگزین رمزنگاری یا جداسازی حساب نیست؛ هر کسی که به پروفایل مرورگر دسترسی دارد ممکن است داده‌ها را ببیند.
3. جمع‌آوری شماره تماس، جنسیت و جزئیات پزشکی برای کارکرد پایه یک دوره آموزشی باید توجیه شود؛ «شاید در آینده لازم شود» دلیل کافی نیست.
4. وجود دو نسخه از پروفایل باعث ناسازگاری و باقی‌ماندن داده پس از پاک‌سازی ناقص می‌شود.
5. آرشیو می‌تواند متن‌های حساس گذشته را نگه دارد، حتی وقتی کاربر تصور کند مسیر جدید را آغاز کرده است.
6. پاک‌کردن مرورگر/حافظه برنامه ممکن است داده را از دسترس کاربر خارج کند؛ راهکار export/import امن فعلاً در ممیزی کد پیدا نشد.
7. بررسی فعلی اثبات نمی‌کند که هیچ telemetry یا log در لایه میزبانی وجود ندارد. بررسی DevTools network، تنظیمات GitHub Pages/CDN و فایل‌های workflow جداگانه لازم است.

## ۵. قواعد غیرقابل‌مذاکره پیش از AI ابری

- هیچ متن آزاد، پاسخ ارزیابی، یادداشت پزشکی، شماره تماس یا نامی بدون رضایت آگاهانه و مشخص به سرویس مدل ارسال نشود.
- پیش‌فرض باید «ارسال‌نکردن داده حساس» باشد؛ نه opt-out پنهان.
- قبل از ارسال، حذف نام/شماره تماس و سایر شناسه‌ها انجام شود؛ اما de-identification به‌تنهایی ناشناس‌سازی قطعی نیست.
- متن ارسالی به مدل باید به حداقل داده لازم برای همان پاسخ محدود شود.
- کلید API مدل هرگز در کد مرورگر یا bundle قرار نگیرد؛ درخواست‌ها از backend کنترل‌شده عبور کنند.
- backend باید احراز هویت، کنترل دسترسی، rate limit، ثبت رویداد حداقلی، سیاست نگهداری و حذف، و مدیریت secret داشته باشد.
- provider، منطقه پردازش، مدت نگهداری، استفاده یا عدم استفاده برای آموزش، subprocessors و قرارداد پردازش داده قبل از انتخاب سرویس بررسی شوند.
- حافظه بلندمدت AI فقط با opt-in جداگانه، امکان مشاهده/اصلاح/حذف و توضیح روشن فعال شود.
- کاربر باید بتواند از اپ استفاده کند حتی اگر با پردازش ابری یا حافظه AI موافقت نکند.

## ۶. تصمیم‌های اجرایی پیشنهادی

### P0 — قبل از هر API یا AI
1. تصمیم مالک درباره ضرورت واقعی هر فیلد پروفایل؛ به‌خصوص شماره تماس، جنسیت، سن و فیلدهای پزشکی/دارویی.
2. طراحی یک مدل canonical برای پروفایل؛ حذف تکرار بین `profileData` در journey و `PROFILE_KEY` با migration قابل بازگشت.
3. طراحی قابلیت مشاهده، export و حذف همه داده‌های محلی شامل مسیر جاری، آرشیو، پروفایل و نسخه‌های ذخیره‌شده کاربر؛ کتاب‌های seed عمومی فقط در صورت نیاز reset شوند.
4. طراحی رضایت تفکیک‌شده برای داده سلامت، پردازش ابری و حافظه بلندمدت.
5. ثبت Data Flow Diagram و Threat Model با مرزبندی مرورگر، میزبان، backend و provider.
6. بررسی عملی network requests، headers، CSP، telemetry، GitHub Pages و هر CDN احتمالی.

### P1 — پیش از پایلوت
1. تعریف retention و deletion job برای داده‌های سمت سرور.
2. رمزنگاری انتقال TLS و رمزنگاری داده‌های سرور در حالت سکون با مدیریت کلید.
3. جلوگیری از ثبت متن‌های آزاد حساس در application logs، error trackers و analytics.
4. تست XSS، کنترل خروجی محتوای کاربر، CSRF در backend و کنترل دسترسی.
5. تست export/import و حذف روی نسخه‌های قدیمی state و archive.

## ۷. مواردی که عمداً انجام نشد

- رمزنگاری localStorage با کلید ثابت داخل bundle اضافه نشد؛ چنین کاری امنیت واقعی ایجاد نمی‌کند و می‌تواند حس امنیت کاذب بدهد.
- حذف فیلدهای پزشکی یا شماره تماس از schema فعلی بدون migration و بررسی اثر محصول انجام نشد.
- هیچ داده‌ای از کاربر به مدل یا سرویس خارجی ارسال نشد.
- هیچ ادعای انطباق GDPR یا قانون محلی مطرح نمی‌شود؛ ارزیابی حقوقی با توجه به کشورها و بازار هدف لازم است.


## ۸. قابلیت‌های محلی خروجی و حذف — پیاده‌سازی در شاخه توسعه

در صفحه پشتیبانی، بخش «حریم خصوصی و داده‌های من» اضافه شد:
- خروجی JSON از کلیدهای برنامه با پیشوند `maseer28_` به‌جز پذیرش حق نشر، به‌علاوه پرچم قدیمی `profile_completed`.
- حذف همین کلیدهای متعلق به برنامه با تأیید صریح کاربر.
- نگهداری داده‌های سایت‌های دیگر و پرچم پذیرش حق نشر دست‌نخورده می‌ماند.
- کتاب‌های seed و محتوای عمومی IndexedDB حذف نمی‌شوند؛ در کد فعلی آن پایگاه برای محتوای کتابخانه استفاده شده است.

**محدودیت مهم:** این قابلیت فقط داده‌های localStorage همین مرورگر را پوشش می‌دهد. فایل‌های export دانلودشده، نسخه‌های پشتیبان سیستم، داده‌های احتمالی سمت سرور یا داده‌هایی که خارج از مرورگر پردازش شده‌اند حذف نمی‌شوند. چون در نسخه فعلی حساب و backend داده کاربر وجود ندارد، حذف سمت سرور از این قابلیت ادعا نمی‌شود.

سورس: `src/features/privacy/localData.js` و کنترل‌های صفحه پشتیبانی. آزمون‌های export/delete در `tests/localData.test.mjs` اضافه شده‌اند.
