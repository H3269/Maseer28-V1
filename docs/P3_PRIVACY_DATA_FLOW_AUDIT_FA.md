# ممیزی جریان داده، پشتیبان و حذف اطلاعات — P3

تاریخ ممیزی: 2026-11-03  
شاخه بررسی‌شده: `p3/controlled-restore-executor`  
مبنای ممیزی: کد شاخه و تست‌های موجود؛ این سند به‌تنهایی تأیید امنیت مستقل یا پذیرش میزبان Telegram/Bale نیست.

## 1. خلاصه تصمیم

- خروجی ZIP/PDF آرشیو از آرایه آرشیو مسیرها تولید می‌شود و نام، شماره تماس و غربالگری پزشکی پروفایل مستقل را از منبع جداگانه نمی‌خواند.
- محتوای آرشیو همچنان حساس است: مسئله مسیر، هدف، پاسخ‌های روزانه، امتیازها، بازخوردها و گزارش نهایی می‌توانند داده روان‌شناختی قابل انتساب باشند.
- پشتیبان کامل JSON عمداً همه کلیدهای متعلق به برنامه در localStorage را به همراه رکوردهای کاربر IndexedDB صادر می‌کند؛ بنابراین پروفایل مستقل و داده مسیر نیز داخل آن قرار می‌گیرند.
- فایل JSON پشتیبان رمزگذاری نمی‌شود. checksum فعلی FNV-1a-32 غیررمزنگارانه است و فقط برای تشخیص تغییر/خرابی تصادفی مناسب است؛ محرمانگی، اصالت یا هویت سازنده را تضمین نمی‌کند.
- حذف انتخابی آرشیو در UI به executor دارای read-back و rollback جبرانی متصل است؛ اما حذف کامل چندمخزنی، حذف مستقل پروفایل و بازیابی backup هنوز نباید به‌عنوان قابلیت UI تأییدشده معرفی شوند.

## 2. ماتریس جریان داده

| جریان | داده‌های داخل دامنه | موارد خارج از دامنه/محدودیت |
|---|---|---|
| ZIP/PDF آرشیو | داده‌های آرشیو، مسئله مسیر، پاسخ‌ها، امتیازها، بازخوردها، تاریخ‌ها و محتوای گزارش/روزها | پروفایل مستقل جداگانه خوانده نمی‌شود؛ فایل رمزگذاری نشده و متن PDF تصویری/غیرقابل جست‌وجو است |
| پشتیبان کامل JSON | کلیدهای `maseer28_*` به‌جز پذیرش حق نشر، `profile_completed` و رکوردهای کاربر در سه store کتابخانه | فایل رمزگذاری نشده؛ فایل دانلودشده و کپی‌های سیستم‌عامل با حذف مرورگر پاک نمی‌شوند |
| بازیابی JSON | فقط نسخه پشتیبانی‌شده، فضای بدون تعارض، کلیدهای مجاز و schema سازگار؛ نوشتن IndexedDB تراکنشی و جبران localStorage | checksum احراز اصالت نیست؛ بازیابی چندمخزنی تراکنش اتمیک مشترک ندارد؛ API هنوز به UI متصل نشده است |
| حذف انتخابی آرشیو | دقیقاً یک عضو آرایه archive از snapshot مسیر حذف و read-back می‌شود | خروجی‌ها/backupهای دانلودشده، مسیر فعال و پروفایل مستقل حذف نمی‌شوند |
| حذف کامل داده محلی | helperهای localStorage و IndexedDB هر کدام namespace خود را حذف و راستی‌آزمایی می‌کنند | حذف دو مخزن یک تراکنش اتمیک مشترک نیست؛ orchestration و گزارش نتیجه جزئی باید در UI بررسی/تکمیل شود |
| نگهداری آرشیو | سقف عملیاتی ۲۰ رکورد؛ داده قدیمی بیشتر از سقف هنگام hydrate حفظ می‌شود | سقف تعداد، سیاست retention زمانی نیست؛ تاریخ انقضای مصوب وجود ندارد |

## 3. شواهد کد

- `src/features/privacy/localData.js`: تابع `readLocalUserData` تمام کلیدهای متعلق به برنامه را صادر می‌کند؛ بنابراین کلیدهای پروفایل مستقل نیز در پشتیبان JSON قرار می‌گیرند. تابع حذف فقط localStorage را پوشش می‌دهد.
- `src/features/privacy/indexedDbData.js`: خروجی و حذف داده‌های کاربر IndexedDB را از داده‌های seed تفکیک می‌کند. حذف IndexedDB مستقل از حذف localStorage انجام می‌شود.
- `src/features/privacy/privacyBackup.js`: نسخه پشتیبان 3.0.0 شامل localStorage و داده‌های کاربر IndexedDB است. الگوریتم integrity با عنوان صریح `fnv1a-32-non-cryptographic` ثبت شده است. بازیابی در صورت تعارض متوقف می‌شود و overwrite انجام نمی‌دهد.
- `src/features/journey/archiveExport.js`: PDF از فیلدهای آرشیو ساخته می‌شود و تابع export فقط آرایه آرشیو را دریافت می‌کند؛ این مسیر به پروفایل مستقل دسترسی ندارد.
- `src/features/journey/journeyStore.js`: `cloneForArchive` فقط فیلدهای مسیر را نگه می‌دارد؛ حذف انتخابی آرشیو با بررسی شاخص و read-back انجام می‌شود.
- `src/features/journey/JourneyScreens.jsx`: خروجی ZIP/PDF به UI آرشیو متصل است. import شدن helperهای پشتیبان/حذف به‌تنهایی اثبات اتصال UI نیست؛ در این فایل فراخوانی اجرایی متناظر برای ساخت/بازیابی پشتیبان یا حذف کامل دیده نشد.

## 4. ریسک‌ها و تصمیم‌های باز

### P3-DATA-01 — پشتیبان JSON حاوی داده حساس و بدون رمزگذاری
شدت: بالا برای محرمانگی فایل خروجی.

پشتیبان کامل، پروفایل مستقل و داده‌های مسیر را کنار هم نگه می‌دارد. این رفتار برای بازیابی کامل قابل فهم است، اما کاربر باید پیش از تولید فایل بداند که فایل شامل اطلاعات هویتی/تماسی، غربالگری پزشکی و پاسخ‌های خصوصی است. checksum فعلی نباید به‌عنوان «امن‌سازی» یا «رمزگذاری» معرفی شود.

اقدام لازم:
1. پیش از اتصال UI، صفحه/مرحله تأیید دامنه داده‌های داخل backup و هشدار ذخیره امن فایل طراحی شود.
2. اگر رمزگذاری فایل در محصول لازم است، از طرح رمزنگاری استاندارد و کتابخانه/قابلیت مرورگر بازبینی‌شده استفاده شود؛ الگوریتم اختصاصی ساخته نشود.
3. تست‌ها باید وجود فیلدهای حساس در backup کامل را به‌عنوان رفتار عمدی و مستند تثبیت کنند.

### P3-DATA-02 — حذف کامل چندمخزنی و وضعیت شکست جزئی
شدت: بالا برای صحت ادعای حذف.

localStorage و IndexedDB به صورت مستقل حذف می‌شوند و تراکنش اتمیک مشترک ندارند. نتیجه موفق یک helper، موفقیت حذف در مخزن دیگر را اثبات نمی‌کند.

اقدام لازم:
1. یک executor هماهنگ‌کننده با preflight، ثبت نتیجه هر مخزن، read-back و وضعیت صریح `partial_delete/recovery_required` طراحی شود.
2. شکست هر مرحله نباید با پیام «همه داده‌ها حذف شد» نمایش داده شود.
3. تست خطا برای شکست قبل/بعد از حذف هر مخزن و بازخوانی پس از reload اضافه شود.

### P3-DATA-03 — قابلیت‌های آماده‌سازی‌شده اما متصل‌نشده به UI
شدت: متوسط تا بالا برای صحت محصول.

توابع پشتیبان/بازیابی و helperهای حذف در ماژول‌ها وجود دارند، اما وجود import یا API داخلی به معنی قابلیت قابل استفاده کاربر نیست. در ممیزی فایل `JourneyScreens.jsx` اتصال اجرایی متناظر برای backup/restore و حذف کامل پیدا نشد.

اقدام لازم:
1. پیش از ادعای وجود قابلیت در اپ، محل UI و مسیر واقعی کاربر مشخص و با آزمون مرورگر پوشش داده شود.
2. اگر تصمیم محصول فعلاً عدم ارائه restore است، مسیر UI و متن مستندات باید صریحاً آن را «پیاده‌سازی داخلی، غیرفعال برای کاربر» بنامند.

### P3-DATA-04 — ذخیره محلی داده‌های حساس
شدت: بالا در مدل تهدید دستگاه مشترک یا کد مخرب هم‌مبدأ.

پروفایل مستقل همچنان در localStorage و داده کتابخانه در IndexedDB مرورگر ذخیره می‌شود. جداسازی منطقی پروفایل از snapshot مسیر، رمزگذاری یا کنترل دسترسی ایجاد نمی‌کند. راهنمای OWASP نیز هشدار می‌دهد که localStorage و IndexedDB محرمانگی در برابر دسترسی به پروفایل مرورگر یا اسکریپت مخرب هم‌مبدأ فراهم نمی‌کنند.

اقدام لازم:
1. تا پیش از تصمیم معماری سرور/رمزگذاری، هیچ ادعای ذخیره امن یا حفاظت در برابر دسترسی دستگاه مطرح نشود.
2. هرگونه انتقال آینده به سرور مادر باید با حداقل‌سازی داده، کنترل دسترسی و سیاست حذف سمت سرور طراحی شود.
3. سطح حمله XSS و سیاست CSP/امنیت خروجی‌ها در ممیزی مستقل جداگانه بررسی شود.

### P3-DATA-05 — retention فقط بر اساس ظرفیت، نه زمان
شدت: متوسط.

سقف ۲۰ آرشیو جلوی رشد نامحدود تعداد را در مسیر جدید می‌گیرد، اما زمان نگهداری داده را تعیین نمی‌کند. آرشیوهای قدیمی‌تر از ۲۰ نیز هنگام بارگذاری خودکار حذف نمی‌شوند.

اقدام لازم:
1. مدت نگهداری، مبنای شروع شمارش، امکان تمدید، اطلاع‌رسانی و استثناهای حقوقی باید تصمیم محصولی/حقوقی جداگانه داشته باشد.
2. تا تصویب آن، از اعلام هر مدت مشخص یا ادعای retention کامل خودداری شود.

## 5. آزمون‌های الزامی مرحله بعد

- Backup کامل: وجود پروفایل مستقل، مسیر فعال، آرشیوها و داده کاربر IndexedDB در خروجی؛ نبود کلید پذیرش حق نشر و داده seed عمومی.
- Archive export: عدم حضور فیلدهای name/phone/medical/medication/medicalNote در PDF/ZIP حتی وقتی رکورد legacy ورودی این فیلدها را دارد؛ حضور محتوای مسیر برای خروجی آرشیو مورد انتظار است.
- Restore: تعارض کلید، schema ناسازگار، فایل دستکاری‌شده، خطای IndexedDB و خطای localStorage؛ هیچ overwrite ناخواسته‌ای رخ ندهد.
- حذف کامل: حذف مستقل هر namespace، شکست جزئی، read-back و پیام UI منطبق با نتیجه واقعی.
- Android WebView داخل Telegram و Bale: دانلود فایل و حفظ/پاک‌سازی محلی فقط با آزمون روی دستگاه واقعی تأیید می‌شود.

## 6. نتیجه ممیزی این بخش

**تأیید مشروط:** جداسازی پروفایل از snapshot مسیر و محدود بودن منبع ZIP/PDF آرشیو از نظر کد بررسی‌شده قابل دفاع است.

**تأییدنشده:** محرمانگی فایل backup، رمزگذاری داده‌های محلی، حذف کامل چندمخزنی، اتصال UI بازیابی، retention زمانی و پذیرش واقعی Telegram/Bale.

این بخش فقط پس از اجرای آزمون‌های بخش ۵، تصمیم محصول درباره backup رمزگذاری‌شده و تکمیل executor حذف چندمخزنی قابل بستن است.


## 7. به‌روزرسانی اجرای حذف هماهنگ‌شده

در commit `f907e77` ماژول `src/features/privacy/dataDeletion.js` اضافه شد. تابع `executeCompleteLocalDataDeletion`:
- پیش از هر حذف، امکان enumerate کردن localStorage و خواندن ساختار/داده IndexedDB را بررسی می‌کند.
- در صورت شکست preflight، بدون تغییر داده‌ها متوقف می‌شود.
- هر دو مخزن را جداگانه حذف و نتیجه هرکدام را read-back می‌کند.
- فقط در صورت تأیید خالی بودن هر دو namespace وضعیت `complete` می‌دهد.
- در شکست قابل مشاهده یک مخزن وضعیت `partial_delete` و در وضعیت نامطمئن/خطای راستی‌آزمایی وضعیت `recovery_required` می‌دهد.

**محدودیت مهم:** این مجری حذف، تراکنش اتمیک بین localStorage و IndexedDB ایجاد نمی‌کند و rollback بین دو مخزن انجام نمی‌دهد. اگر یکی حذف شود و دیگری شکست بخورد، نتیجه عمداً موفق اعلام نمی‌شود. در commit `8616c4c` دکمه «حذف داده‌های محلی من» در صفحه پشتیبانی به این مجری متصل شد و متن پیام UI بر اساس وضعیت واقعی نتیجه تفکیک شد. آزمون Chromium در commit `94ba751` اتصال UI را بررسی کرد: پس از حذف، برنامه فقط یک مسیر تازه و خالی می‌سازد؛ پروفایل مستقل و داده‌های قبلی بازنمی‌گردند؛ داده نامرتبط مرورگر و پذیرش حق نشر حفظ می‌شوند. این آزمون هنوز پذیرش WebView واقعی Telegram/Bale را اثبات نمی‌کند.

تست‌های جدید در `tests/localData.test.mjs` چهار سناریو را پوشش می‌دهند: حذف کامل با حفظ seed و داده نامرتبط، شکست انتخابی localStorage و گزارش partial، شکست preflight بدون mutation، و شکست مرحله IndexedDB پس از حذف localStorage با گزارش recovery_required.
