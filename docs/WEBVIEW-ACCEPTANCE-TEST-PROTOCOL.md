# پروتکل آزمون پذیرش WebView و قابلیت‌های پشتیبانی

> وضعیت: پروتکل آزمون؛ هنوز اجرای میدانی روی دستگاه واقعی انجام نشده است.
> شاخه: `p3/controlled-restore-executor`
> تاریخ: 2026-11-03
> مکمل سند: `docs/ENVIRONMENT-WEBVIEW-COMPATIBILITY-MATRIX.md`

## 1. هدف و اصول اجرا

این پروتکل برای تفکیک سه نوع مسئله است:
1. نقص خود کد که مستقل از میزبان وجود دارد.
2. ناسازگاری یا محدودیت میزبان WebView (Telegram/Bale).
3. خطای محیط دستگاه، مجوز یا تنظیمات کاربر.

هر نتیجه باید در هر دو میزبان جداگانه ثبت شود. نتیجه Chrome به‌تنهایی پذیرش Telegram یا Bale محسوب نمی‌شود.

**ممنوعیت‌های آزمون**
- از پرونده واقعی یا اطلاعات هویتی/پزشکی واقعی استفاده نکنید؛ فقط داده ساختگی.
- روی حساب یا داده اصلی کاربر، حذف داده یا restore انجام ندهید.
- نسخه آزمایشی را با داده کاربران واقعی جایگزین نکنید.
- بدون تأیید مالک، build را منتشر یا PR را merge نکنید.
- در گزارش، شماره تلفن، پاسخ روان‌شناختی یا محتوای پشتیبان واقعی درج نکنید.

## 2. اطلاعات اجباری هر اجرای آزمون

برای هر سناریو یک ردیف مستقل ثبت شود:
- شناسه آزمون و تاریخ/ساعت محلی
- میزبان: Telegram یا Bale (نام دقیق برنامه)
- نسخه برنامه میزبان
- مدل دستگاه و نسخه Android
- URL و شناسه build/commit برنامه
- وضعیت اتصال اینترنت
- مراحل بازتولید دقیق
- نتیجه مورد انتظار و نتیجه واقعی
- PASS / FAIL / BLOCKED / NOT RUN
- تصویر یا ویدئوی شاهد، بدون داده حساس
- گزارش خطا یا کنسول، در صورت دسترسی

اگر شناسه build یا commit معلوم نیست، نتیجه فقط «مشاهده مقدماتی» است و پذیرش نهایی محسوب نمی‌شود.

## 3. سناریوهای آزمون

### WV-01 — راه‌اندازی و چرخه عمر WebView
**مراحل**
1. اپ را از لینک رسمی در میزبان باز کنید.
2. تا داشبورد صبر کنید.
3. میزبان را به پس‌زمینه ببرید و دوباره بازگردید.
4. WebView را refresh کنید، اگر میزبان این امکان را می‌دهد.
5. اتصال اینترنت را یک‌بار قطع و وصل کنید.

**قبولی**
- صفحه بدون خطای سفید/قفل دائمی باز شود.
- پس از بازگشت، داده محلی مورد انتظار حفظ شود.
- refresh باعث ساخت پرونده تکراری یا پاک‌شدن داده نشود.

### WV-02 — چیدمان و ناوبری
**مراحل**
1. خانه، پروفایل، کتابخانه و پشتیبانی را باز کنید.
2. در هر صفحه به بالا و پایین اسکرول کنید.
3. Bottom navigation و header را در جهت‌های مختلف اسکرول بررسی کنید.
4. دستگاه را در صورت پشتیبانی میزبان بچرخانید.

**قبولی**
- دکمه‌های اصلی قابل لمس و قابل مشاهده باشند.
- header یا bottom navigation روی محتوای حیاتی نیفتد.
- در Bale، قواعد `bale-webview` باعث برش یا فضای خالی غیرعادی نشوند.

### WV-03 — خروجی JSON
**پیش‌شرط:** فقط داده آزمایشی ساختگی در localStorage و IndexedDB.

**مراحل**
1. به صفحه پشتیبانی و بخش «حریم خصوصی و داده‌های من» بروید.
2. «دریافت نسخه اطلاعات من» را انتخاب کنید.
3. منتظر پایان عملیات بمانید.
4. بررسی کنید فایل واقعاً در دستگاه ذخیره شده یا در مقصد قابل دسترسی قرار گرفته است.
5. فایل را خارج از اپ باز کنید و ساختار JSON را اعتبارسنجی کنید.

**قبولی**
- فایل واقعی وجود داشته باشد؛ پیام موفقیت به‌تنهایی کافی نیست.
- JSON parse شود و schema مورد انتظار backup را داشته باشد.
- داده حساس در نام فایل، URL یا پیام خطا افشا نشود.
- فایل با اندازه صفر یا ناقص PASS نیست.

**شکست**
- هیچ فایل یا مقصد قابل دسترسی وجود ندارد.
- دانلود مسدود/بی‌صدا ناپدید می‌شود.
- فایل خراب یا ناقص است.

### WV-04 — انتخاب و پیش‌نمایش فایل پشتیبان
**مراحل**
1. فایل JSON آزمایشی معتبر را انتخاب کنید.
2. پیش‌نمایش را اجرا کنید.
3. بدون اجرای restore از صفحه خارج شوید.
4. فایل نامعتبر یا فایل بزرگ‌تر از ۱۵ مگابایت را نیز انتخاب کنید.

**قبولی**
- file picker میزبان باز شود و فایل انتخابی به WebView برسد.
- فایل معتبر preview شود و تا پیش از تأیید restore هیچ داده‌ای تغییر نکند.
- فایل نامعتبر یا بیش از حد مجاز رد شود.
- پیام خطا محتوای شخصی یا stack trace را نمایش ندهد.

### WV-05 — Clipboard و صحت پیام موفقیت
**مراحل**
1. در صفحه پشتیبانی، «کپی شماره» را اجرا کنید.
2. در یک برنامه مستقل، paste کنید.
3. آزمون را در شرایطی تکرار کنید که Clipboard API در دسترس نباشد یا عملیات کپی رد شود (در صورت امکان با build آزمون کنترل‌شده).
4. نتیجه پیام UI را با محتوای واقعی clipboard مقایسه کنید.

**قبولی**
- فقط پس از تأیید واقعی عملیات، پیام موفقیت نشان داده شود.
- در صورت شکست یا عدم امکان تأیید، پیام جایگزین و راهکار دستی نمایش داده شود.
- متن pasteشده دقیقاً مقدار مورد انتظار باشد.

**نقص کد از پیش شناسایی‌شده**
تابع کپی به helper مستقل منتقل شده است: Clipboard API ابتدا امتحان می‌شود و در صورت ردشدن، fallback فقط وقتی موفق اعلام می‌شود که `document.execCommand('copy') === true` باشد. این تأیید API هنوز جای آزمون paste واقعی در برنامه میزبان را نمی‌گیرد؛ نتیجه WV-05 در Telegram و Bale تا اجرای میدانی NOT RUN می‌ماند.

### WV-06 — SMS و fallback
**مراحل**
1. «باز کردن پیامک» را لمس کنید.
2. بررسی کنید برنامه پیامک سیستم باز می‌شود یا خیر.
3. وجود شماره و متن پیش‌فرض را بررسی کنید؛ پیامک را ارسال نکنید.
4. مسیر fallback «کپی شماره» را جداگانه آزمایش کنید.

**قبولی**
- برنامه پیامک سیستم با شماره و متن صحیح باز شود، یا fallback صادقانه نمایش داده شود.
- UI بدون شاهد از بازشدن برنامه پیامک ادعای قطعی نکند.
- در صورت شکست scheme، کاربر همچنان بتواند شماره را دستی استفاده کند.

### WV-07 — لینک خارجی تلگرام
**مراحل**
1. لینک پشتیبانی تلگرام را لمس کنید.
2. رفتار میزبان را ثبت کنید: بازشدن درون WebView، مرورگر خارجی، اپ Telegram یا خطا.
3. بازگشت به اپ مسیر۲۸ را بررسی کنید.

**قبولی**
- لینک به مقصد مورد انتظار برسد یا پیام قابل فهم برای ادامه دستی ارائه شود.
- اپ اصلی پس از بازگشت state خود را از دست ندهد.

### WV-08 — کتاب‌خوان
**مراحل**
1. حداقل یک کتاب را باز کنید.
2. متن فارسی، نیم‌فاصله، تیترها و انتهای صفحه را بررسی کنید.
3. اسکرول سریع و آهسته انجام دهید.
4. در Bale عرض محاسبه‌شده اختصاصی را بررسی کنید.

**قبولی**
- متن بریده یا روی‌هم‌افتاده نباشد.
- اسکرول به انتهای محتوا برسد.
- کنترل‌های ناوبری قابل استفاده باشند.

### WV-09 — قفل روزانه در build تولیدی
**پیش‌شرط:** فقط production build تأییدشده و حساب آزمایشی.

**مراحل**
1. مقدارهای build را با artifact تأییدشده تطبیق دهید: `TEST_MODE=false` و `TIME_LOCK_ENABLED=true`.
2. روز جاری را کامل کنید.
3. تلاش برای ورود زودهنگام به روز بعد را انجام دهید.
4. زمان معتبر سرور و سپس خطای دریافت زمان را آزمایش کنید.

**قبولی**
- روز بعد پیش از زمان مجاز باز نشود.
- خطای زمان معتبر به بازشدن آزادانه روزها منجر نشود (fail-closed).
- منطقه زمانی تهران در محاسبه مرز روز اعمال شود.

### WV-10 — آرشیو و حذف انتخابی
**پیش‌شرط:** اجرای این سناریو فقط روی شاخه و build مشخص‌شده؛ رفتار main و P3 جداگانه ثبت شود.

**مراحل**
1. چند مسیر آزمایشی ایجاد و آرشیو کنید.
2. تعداد و محتوای آرشیوها را پس از refresh بررسی کنید.
3. حذف یک آرشیو مشخص را اجرا کنید.
4. در صورت امکان، خطای ذخیره‌سازی را در محیط کنترل‌شده شبیه‌سازی کنید.
5. تلاش برای شروع مسیر جدید در ظرفیت کامل را بررسی کنید.

**قبولی P3**
- داده‌های آرشیو حفظ شوند تا کاربر مورد مشخصی را حذف کند.
- حذف انتخابی فقط همان آرشیو را حذف کند.
- شکست عملیات، پیام موفقیت یا بستن dialog ایجاد نکند.
- شروع مسیر جدید در ظرفیت کامل بدون آزادسازی فضای لازم انجام نشود.

توجه: این معیارها معیار شاخه P3 هستند و نباید به main یا نسخه live نسبت داده شوند تا ادغام/انتشار مجاز انجام نشده است.

## 5. قواعد تصمیم‌گیری پس از آزمون

- **PASS:** همه معیارهای قبولی با شاهد ثبت‌شده برقرارند.
- **FAIL — Code:** نقص مستقل از میزبان بازتولید شده؛ باید issue/اصلاح کد تعریف شود.
- **FAIL — Host:** روی میزبان مشخص شکست می‌خورد و در مرورگر مرجع کار می‌کند؛ باید workaround یا محدودیت محصول بررسی شود.
- **BLOCKED:** پیش‌شرط، مجوز یا دسترسی لازم فراهم نیست؛ شکست محصول محسوب نمی‌شود.
- **NOT RUN:** هنوز اجرا نشده؛ هرگز نباید به‌عنوان PASS گزارش شود.

## 6. گیت پذیرش

هیچ قابلیت خروجی، بازیابی، clipboard، SMS یا لینک خارجی صرفاً بر اساس مشاهده سورس «سازگار با Telegram/Bale» اعلام نمی‌شود.

برای پذیرش:
1. WV-01 تا WV-08 در هر دو میزبان اجرا و ثبت شوند.
2. نقص WV-05 اصلاح و دوباره آزموده شود.
3. WV-09 فقط روی production artifact تأییدشده اجرا شود.
4. WV-10 برای main و P3 با برچسب شاخه جدا ثبت شود.
5. خطاهای بحرانی و از دست رفتن داده صفر باشد.
6. گزارش نهایی به مالک ارائه و تصمیم انتشار جداگانه اخذ شود.

**این سند مجوز انتشار، merge یا تغییر سیاست نگهداری داده نیست.**


### WV-11 — خروجی ZIP/PDF آرشیو
**مراحل**
1. با داده‌های ساختگی حداقل یک مسیر را در آرشیو قرار دهید.
2. «دریافت خروجی ZIP و PDF آرشیوها» را در Telegram و سپس Bale اجرا کنید.
3. وجود فایل ZIP را در پوشه دانلود/فایل‌های دستگاه بررسی کنید.
4. ZIP را باز و PDF داخلی را با یک PDF reader مستقل باز کنید؛ صفحات، متن فارسی و ترتیب مسیرها را بررسی کنید.
5. آزمون را با آرشیو خالی و با خطای شبیه‌سازی‌شده Canvas تکرار کنید.

**قبولی**
- ZIP معتبر و شامل یک PDF برای هر آرشیو ساخته شود.
- PDFها باز شوند و داده مسیر با آرشیو داخل اپ تطابق داشته باشد.
- فایل واقعاً در دستگاه ذخیره یا از مسیر میزبان به کاربر تحویل شود؛ صرف اجرای `a.click()` قبولی نیست.
- در شکست، پیام صادقانه نمایش داده شود و داده محلی دست‌نخورده بماند.

**محدودیت شواهد:** آزمون خودکار Chromium فقط تولید فایل و dispatch دانلود را می‌سنجد؛ پذیرش Telegram/Bale نیازمند دستگاه واقعی است.
