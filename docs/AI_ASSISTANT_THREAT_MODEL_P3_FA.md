# مدل تهدید و جریان داده دستیار مسیر۲۸ — P3

**وضعیت:** پیش‌نویس فنی مبتنی بر بررسی ایستای مخزن؛ نیازمند بازبینی امنیتی مستقل  
**شاخه:** main  
**دامنه:** نسخه وب فعلی و معماری پیشنهادی دستیار آینده  
**محدودیت:** این سند آزمون نفوذ، مشاهده ترافیک واقعی، بررسی CDN/میزبانی یا ممیزی حقوقی نیست.

## 1. دارایی‌ها و مرزهای اعتماد

| دارایی | محل/وضعیت فعلی | سطح حساسیت |
|---|---|---|
| پروفایل | localStorage؛ بخشی در journey state و بخشی در کلید پروفایل | بالا؛ شامل شناسه و داده پزشکی/دارویی |
| پاسخ‌های روزانه و بازتاب | localStorage در `maseer28_state` | بسیار بالا؛ متن آزاد ممکن است سلامت، روابط یا بحران را افشا کند |
| ارزیابی آغاز/پایان | همان journey state | بالا؛ self-report روان‌شناختی و غیرتشخیصی |
| آرشیو مسیر | همان journey state | بسیار بالا؛ نسخه‌های قبلی داده حساس را نگه می‌دارند |
| کتابخانه و نسخه‌ها | IndexedDB با نام `maseer28-library` | متغیر؛ می‌تواند شامل محتوای کاربر و تنظیمات باشد |
| رضایت AI/حافظه | سیاست طراحی موجود؛ رضایت عملیاتی در runtime اثبات نشده | بحرانی برای هر پردازش ابری |
| کد پرونده/مسیر | شناسه سمت‌کاربر | به‌تنهایی راز یا عامل احراز هویت نیست |
| کلید ارائه‌دهنده مدل | Backend هنوز پیاده‌سازی نشده | باید secret سمت سرور باشد؛ هرگز در bundle مرورگر قرار نگیرد |

مرزهای اعتماد:
1. مرورگر و داده‌های ذخیره‌شده روی دستگاه؛
2. کد عمومی و فایل‌های قابل دانلود اپ؛
3. Backend آینده و پایگاه داده؛
4. ارائه‌دهنده مدل و پردازشگرهای فرعی؛
5. ابزارهای telemetry، گزارش خطا و CI/CD؛
6. کاربر، متن آزاد، فایل‌های بارگذاری‌شده و اسناد بازیابی‌شده به‌عنوان ورودی غیرقابل‌اعتماد.

## 2. جریان داده فعلی که از کد قابل مشاهده است

- داده مسیر و پروفایل در localStorage نگهداری می‌شود.
- پروفایل از `profileData` مسیر به `maseer28_user_profile_v1` مهاجرت می‌کند و ممکن است در دو کلید باقی بماند.
- داده کتابخانه در IndexedDB با سه object store به نام‌های `books`, `versions`, `settings` نگهداری می‌شود.
- ماژول `localData.js` برای export/delete فقط کلیدهای localStorage متعلق به اپ را می‌خواند/پاک می‌کند؛ IndexedDB، فایل دانلودشده، backup سیستم‌عامل و داده سمت سرور را پوشش نمی‌دهد.
- در کد بررسی‌شده اتصال مدل ابری یا API دستیار اثبات نشده است. این مشاهده، لاگ‌های احتمالی میزبان/CDN یا تنظیمات خارج از مخزن را ارزیابی نمی‌کند.

## 3. سناریوهای تهدید و کنترل‌های الزامی

| شناسه | سناریو | پیامد | کنترل/معیار آزمون |
|---|---|---|---|
| TM-01 | XSS یا اسکریپت مخرب هم‌مبدأ localStorage را بخواند | افشای پروفایل و متن‌های حساس | CSP متناسب، حذف sinkهای ناامن، وابستگی حداقلی، تست XSS؛ عدم ادعای رمزنگاری localStorage |
| TM-02 | دستگاه مشترک/گم‌شده یا پروفایل مرورگر مشترک | دسترسی فیزیکی به داده ذخیره‌شده | هشدار روشن درباره ذخیره محلی، قفل دستگاه، امکان پاک‌سازی کامل و عدم ذخیره داده غیرضروری |
| TM-03 | حذف ناقص داده | باقی‌ماندن داده در کلید دیگر یا IndexedDB | موجودی جامع همه storageها، export/delete قابل‌تأیید، تست بعد از حذف و توضیح محدودیت backup/export |
| TM-04 | مهاجرت یا کپی پروفایل به دو محل | عدم سازگاری و حذف ناقص | منبع حقیقت واحد، مهاجرت نسخه‌دار، تست سازگاری و rollback بدون از دست‌دادن داده |
| TM-05 | شناسه پرونده قابل حدس/جعل به‌عنوان احراز هویت استفاده شود | دسترسی غیرمجاز به پرونده | شناسه تصادفی غیرقابل‌حدس به‌علاوه احراز هویت واقعی؛ authorization سمت سرور در هر درخواست |
| TM-06 | درخواست دستیار با شناسه کاربر دیگر ارسال شود | افشای بین‌کاربری | استخراج subject از نشست احراز‌شده، نه از body؛ tenant isolation و تست منفی بین دو حساب |
| TM-07 | متن آزاد حساس به مدل یا لاگ ارسال شود | افشای داده به پردازشگر/لاگ | رضایت مجزا، حذف شناسه، allowlist فیلدهای زمینه، redaction و ممنوعیت log body |
| TM-08 | کلید مدل در bundle یا source map منتشر شود | سوءاستفاده مالی/دسترسی به provider | فقط secret manager سمت سرور، اسکن secret در CI، چرخش کلید و محدودیت هزینه |
| TM-09 | Prompt Injection در متن کاربر/کتاب/بازیابی | افشای داده یا اجرای ابزار ناخواسته | جداسازی دستور از داده، ابزارهای allowlist، مجوز سمت سرور و تأیید صریح اقدام مهم |
| TM-10 | پاسخ مدل با ادعای تشخیص یا دستور دارویی | آسیب سلامت | مرزبندی محصول، سیاست امتناع/ارجاع، تست‌های بحران و بازبینی متخصص |
| TM-11 | telemetry یا error reporting متن حساس را ثبت کند | افشای ناخواسته در سرویس ثالث | عدم ثبت payload، بررسی SDK و network capture، تست redaction |
| TM-12 | انتشار ref یا artifact آزمون‌نشده | ورود کد ناامن به محصول | pin کردن actions، محدودیت ref، approval محیط production و انتشار فقط artifact تأییدشده |

## 4. مدل مجوزدهی پیشنهادی برای Backend

- هویت کاربر از نشست امن سمت سرور استخراج شود؛ هرگز از `userId` یا `caseCode` ارسالی کلاینت به‌عنوان مدرک مالکیت استفاده نشود.
- هر رکورد دارای `owner_subject_id` باشد و هر query/update/delete با owner احراز‌شده محدود شود.
- دسترسی پشتیبانی/اپراتور پیش‌فرض وجود نداشته باشد؛ در صورت نیاز، نقش محدود، دلیل دسترسی، زمان انقضا و audit بدون متن حساس لازم است.
- شناسه پرونده فقط برای ارجاع انسانی/پشتیبانی است و باید از credential و session token مستقل باشد.
- آزمون منفی الزامی: حساب A نباید با تغییر شناسه مسیر/پرونده بتواند داده حساب B را بخواند، تغییر دهد، export یا حذف کند.

## 5. آزمون‌های پذیرش پیش از اتصال مدل

1. آزمون مرورگر/شبکه ثابت کند داده حساس بدون رضایت و بدون ضرورت از دستگاه خارج نمی‌شود.
2. تمام مقصدهای شبکه، SDKها، telemetry و خطاگزارها فهرست و بررسی شوند.
3. export/delete پوشش دقیق localStorage و IndexedDB را اعلام کند و نتیجه حذف را پس از reload بررسی کند.
4. مسیر حذف Backend و backup قبل از جمع‌آوری داده واقعی تعریف و آزموده شود.
5. آزمون tenant isolation و IDOR در Backend با حداقل دو حساب مستقل عبور کند.
6. secret scan نشان دهد هیچ کلید مدل در bundle، source map یا مخزن عمومی نیست.
7. مجموعه Prompt Injection و نشت داده در مسیر RAG و ابزارها عبور کند.
8. سناریوهای خودآسیبی، خطر فوری، خشونت، دارو و خارج از صلاحیت توسط متخصص بازبینی و آزموده شوند.
9. سیاست نگهداری، محل پردازش، subprocessors و withdrawal پیش از اخذ رضایت نهایی اعلام شوند.

## 6. محدودیت‌های دانسته‌شده و کارهای ممنوع فعلی

- هیچ‌یک از کنترل‌های Backend در این سند به معنی پیاده‌سازی یا فعال بودن نیست.
- حذف localStorage به معنی حذف IndexedDB یا server-side deletion نیست.
- localStorage رمزنگاری‌شده توسط اپلیکیشن فرض نمی‌شود.
- کد پرونده، path ID یا شناسه تصادفی جایگزین احراز هویت نیست.
- تا عبور از دروازه‌های بالا، ارسال متن آزاد، ارزیابی، پروفایل یا آرشیو به مدل ابری ممنوع باقی می‌ماند.
- این سند گواهی انطباق GDPR یا قانون دیگری نیست و باید توسط متخصص امنیت، حریم خصوصی و مشاور حقوقی بررسی شود.


## 7. وضعیت واقعی pin کردن Actions در مخزن

در بازبینی workflowهای مخزن، workflow اعتبارسنجی و انتشار آزمایشی از قبل Actionها را با SHA ثابت فراخوانی می‌کردند؛ workflow انتشار GitHub Pages هنوز از برچسب‌های متغیر نسخه استفاده می‌کرد. فایل `.github/workflows/deploy.yml` اکنون Actionهای checkout، setup-node، configure-pages، upload-pages-artifact و deploy-pages را به commit SHAهای مشخص متصل می‌کند تا تغییر ناخواسته tag در آینده، رفتار pipeline را بی‌صدا عوض نکند.

این اقدام ریسک تغییرپذیری tag را کاهش می‌دهد، اما جای بازبینی دوره‌ای نسخه‌ها، کنترل وابستگی‌ها و محدودسازی دسترسی محیط انتشار را نمی‌گیرد.
