# معماری امنیت، نشست، رضایت و محدودسازی دستیار مسیر۲۸ — نسخه ۱

**وضعیت:** تصمیم معماری پیشنهادی؛ هنوز پیاده‌سازی یا فعال نشده است  
**مخزن:** `H3269/Maseer28-V1` — شاخه مجاز: فقط `main`  
**Backend هدف:** Worker موجود `still-firefly-9435maseer28-archive`  
**اصل ایمنی:** تا بسته‌شدن دروازه‌های این سند، endpoint مکالمه باید fail-closed بماند و هیچ متن واقعی کاربر به مدل یا پردازشگر بیرونی ارسال نشود.

## ۱. محدوده و فرض‌های ممنوع

- CORS احراز هویت نیست؛ فقط سیاست دسترسی مرورگر است. Origin قابل جعل خارج از مرورگر است.
- شناسه پرونده، پروفایل، داده پزشکی یا هویت کاربر نباید در توکن دستیار یا payload مدل قرار گیرد.
- یک نشست ناشناس، اثبات هویت یا مجوز دسترسی به پرونده نیست.
- رضایت برای استفاده از اپ، رضایت برای پردازش ابری متن روان‌شناختی نیست.
- ذخیره تاریخچه مکالمه برای نسخه نخست لازم نیست و باید حذف‌شده باقی بماند.
- وجود secret در Worker به‌تنهایی هویت کاربر، رضایت یا ایمنی محتوا را ثابت نمی‌کند.

## ۲. تصمیم نشست و احراز هویت

### طرح پیشنهادی مرحله‌ای

1. **پیش‌نیاز هویت میزبان:** پیش از عرضه عمومی باید مشخص شود اپ در چه محیطی اجرا می‌شود و آیا assertion قابل‌اعتبارسنجی از میزبان/حساب کاربر وجود دارد. اگر اپ Telegram Mini App باشد، اعتبارسنجی امضای `initData` باید فقط سمت Worker و با bot token محرمانه انجام شود؛ اگر میزبان دیگری است، باید روش معادل و مستند آن انتخاب شود. پارامترهای ارسالی از کلاینت بدون امضای معتبر قابل اعتماد نیستند.
2. **نشست کوتاه‌عمر:** پس از اعتبارسنجی میزبان، Worker یک bearer token امضاشده HMAC-SHA-256 صادر کند؛ کلید فقط در Worker Secret باشد. توکن پیشنهادی شامل `iss`, `aud`, `iat`, `exp`, `jti`, `scope` و شناسه تصادفی غیرقابل‌استنتاج نشست باشد. عمر اولیه حداکثر ۱۰ دقیقه؛ تمدید فقط با اعتبارسنجی مجدد assertion میزبان.
3. **حداقل امتیاز:** scope فقط `assistant:turn` باشد. توکن فاقد user ID، پرونده، نام، شماره تماس، داده پزشکی یا تاریخچه گفتگو باشد.
4. **ارسال توکن:** فقط در `Authorization: Bearer`؛ نه query string، نه URL، نه localStorage دائمی و نه cookie دارای نشست. کلاینت تا حد امکان توکن را فقط در حافظه نگه دارد. پاسخ‌ها `Cache-Control: no-store` داشته باشند.
5. **اعتبارسنجی:** امضا، issuer، audience، زمان صدور/انقضا، scope و ساختار claimها در هر درخواست بررسی شود. انقضا و خطای اعتبارسنجی باید fail-closed باشد.

### محدودیت مهم

تا زمانی که نوع میزبان و assertion واقعی آن در کد اپ شناسایی و آزموده نشده، صدور نشست ناشناس عمومی را نباید «احراز هویت کاربر» نامید یا برای دسترسی به داده پرونده به کار برد. اگر assertion معتبر در دسترس نباشد، نسخه آزمایشی فقط باید با داده ساختگی و دسترسی محدود اجرا شود.

## ۳. محدودسازی نرخ و مقابله با سوءاستفاده

- محدودسازی باید سمت سرور باشد؛ محدودیت UI و CORS قابل دور زدن‌اند.
- گزینه پیشنهادی برای مرحله اول: Durable Object مبتنی بر SQLite به‌عنوان شمارنده اتمیک و هماهنگ، با یک bucket کوتاه‌مدت برای نشست و یک سقف ثانویه برای مبدأ شبکه.
- کلید bucket از HMAC سمت سرور روی شناسه نشست یا IP به‌همراه salt دوره‌ای ساخته شود؛ IP خام و شناسه پرونده در جدول شمارنده ذخیره نشوند. hash یا HMAC همچنان داده مستعارشده و نیازمند حفاظت است.
- مقدارهای اولیه صرفاً برای تست و قابل تنظیم: حداکثر ۲۰ درخواست مکالمه در هر ۱۰ دقیقه برای هر نشست و سقف محافظه‌کارانه‌تر برای هر bucket شبکه. این اعداد قبل از پایلوت باید با بار واقعی و خطر سوءاستفاده بازتنظیم شوند؛ سقف شبکه نباید کاربران یک شبکه مشترک را بی‌دلیل مسدود کند.
- درخواست‌های bootstrap نیز باید محدود شوند؛ در غیر این صورت مهاجم می‌تواند با گرفتن مداوم نشست تازه، محدودیت نشست را دور بزند.
- شمارنده‌ها فقط metadata حداقلی داشته باشند؛ TTL/پاکسازی قطعی و آزمون حذف لازم است.
- در خطای Durable Object یا رسیدن به سقف سهمیه، endpoint حساس fail-closed و پاسخ 429/503 بدهد؛ هرگز محدودسازی را به‌طور خاموش bypass نکند.
- برای کاهش بار، یک درخواست Worker می‌تواند یک عملیات DO را انجام دهد. سهمیه DO و Worker جداگانه پایش شود.

## ۴. محدودیت درخواست و اعتبارسنجی ورودی

- فقط `POST /v1/assistant/turn` با `Content-Type: application/json` و body محدود؛ سقف اولیه پیشنهادی ۸ KiB.
- خواندن body باید با سقف واقعی stream انجام شود؛ صرف بررسی `Content-Length` کافی نیست.
- ساختار مجاز فقط نسخه قرارداد، شناسه تصادفی نشست، متن پیام و شناسه‌های context غیرحساسِ مجاز باشد. هر فیلد ناشناخته رد شود.
- سقف پیام اولیه پیشنهادی ۲٬۰۰۰ نویسه Unicode؛ سقف تعداد پیام‌های context نیز محدود و مجموع payload کنترل شود.
- فایل، تصویر، صوت، ZIP، PDF، HTML و URLهای دلخواه در نسخه اول پذیرفته نشوند.
- JSON خراب، body بزرگ، فیلد اضافه، رشته خالی، متن بیش از حد، encoding نامعتبر و نوع داده نادرست باید با خطای کنترل‌شده رد شوند.
- timeout برای درخواست provider در آینده اجباری است؛ timeout یا خطای provider نباید متن خام را در پاسخ خطا یا log بازتاب دهد.

## ۵. رضایت مستقل، نسخه‌بندی و پس‌گرفتن

- رضایت پردازش ابری باید پیش از اولین ارسال، واضح، جداگانه، آگاهانه و به‌صورت پیش‌فرض خاموش باشد.
- متن رضایت باید نام پردازشگر/دسته پردازشگر، هدف، نوع داده ارسالی، کشور/منطقه پردازش، مدت نگهداری، خطرهای اصلی و روش پس‌گرفتن را توضیح دهد.
- نسخه متن رضایت و تاریخ/زمان پذیرش باید مشخص باشند. تغییر اساسی در provider، مقصد، هدف یا retention نیازمند رضایت مجدد است.
- رد رضایت نباید دسترسی به محتوای اصلی ۳۴ موضوع، تمرین‌ها، آرشیو یا امتیازها را محدود کند.
- پس‌گرفتن رضایت باید از ارسال بعدی فوراً جلوگیری کند؛ حذف داده‌های قابل حذف باید در مسیر مستقل و قابل ممیزی اجرا شود.
- برای اثبات حداقلی رضایت، فقط نسخه سیاست، زمان، وضعیت و شناسه مستعار نشست/حساب ثبت شود؛ متن گفتگو یا اطلاعات پرونده ثبت نشود. مبنای قانونی و مدت نگهداری این رکورد باید پیش از عرضه تعیین شود.
- تا تعیین دقیق پردازشگر، منطقه پردازش و متن حقوقی معتبر، رضایت قابل‌عرضه و ارسال واقعی فعال نشود.

## ۶. نگهداری، حذف و ثبت رویداد

- هیچ تاریخچه مکالمه یا prompt/response خام در Worker، Durable Object، Analytics، error tracker یا log ذخیره نشود.
- log عملیاتی فقط شامل route، status code، زمان اجرا، شناسه خطای تصادفی و نسخه نرم‌افزار باشد؛ از IP خام، Authorization header، body، prompt، پاسخ مدل و شناسه پرونده پرهیز شود.
- پیکربندی logging خود Cloudflare و ابزارهای متصل باید جداگانه بررسی شود؛ «در کد log نمی‌کنیم» به‌تنهایی تضمین عدم ثبت در لایه زیرساخت نیست.
- هر metadata موقت دارای TTL صریح و آزمون پاک‌سازی باشد.
- مسیر withdrawal باید token/consent فعال را بی‌اعتبار کند و مانع ارسال بعدی شود.
- قبل از فعال‌سازی provider، باید نقشه حذف و مدت نگهداری provider بررسی شود؛ حذف از اپ لزوماً به معنی حذف فوری از backup یا سامانه provider نیست.

## ۷. کنترل ایمنی مستقل از مدل

- ورودی قبل از provider از safety gate مستقل و deterministic عبور کند؛ خروجی provider نیز پیش از نمایش دوباره بررسی شود.
- سناریوهای فارسی و فینگلیش برای خودآسیبی، قصد/برنامه/دسترسی به وسیله، خودکشی، تهدید دیگران، سوءاستفاده، بحران حاد و درخواست خارج از دامنه باید آزمون شوند.
- safety gate نباید جایگزین ارزیابی انسانی/اورژانسی شود و نباید تشخیص بالینی قطعی تولید کند.
- تشخیص خطر نباید باعث قفل‌کردن کل محتوای تمرینی اپ شود؛ فقط مسیر مکالمه و پاسخ ایمن را کنترل کند.
- مدل زبانی به‌تنهایی مرجع تصمیم safety نیست.

## ۸. آداپتور مدل و قرارداد خروجی در آینده

- provider-neutral adapter با allowlist provider، timeout، حداکثر token ورودی/خروجی، سقف هزینه، circuit breaker و مدیریت خطا لازم است.
- ارسال فقط پس از رضایت معتبر و حذف شناسه‌های مستقیم/غیرضروری مجاز است. pseudonymization تضمین ناشناس‌سازی کامل نیست.
- خروجی مدل باید JSON ساختاریافته و schema-validated باشد؛ متن آزاد مدل مستقیماً به منطق اپ وصل نشود.
- topic keyها باید دقیقاً از registry واقعی ۳۴ موضوع استخراج و با کلیدهای محتوای اصلی تطبیق داده شوند. کلید ناشناخته یا topic ناموجود رد شود.
- دستیار می‌تواند سؤال روشن‌کننده یا چند پیشنهاد رتبه‌بندی‌شده بدهد؛ انتخاب موضوع نهایی با کاربر است.
- هیچ توصیه یا تشخیص پزشکی قطعی تولید نشود.

## ۱۱. احراز اصالت Mini App در Telegram و Bale — نتیجه بررسی رسمی و وضعیت کد

بررسی مستقیم مستندات رسمی هر دو پلتفرم نشان داد که هر دو `initData` خام و قابل اعتبارسنجی در سمت Backend ارائه می‌کنند و از الگوی HMAC-SHA-256 با کلید `WebAppData` و توکن بازوی/ربات استفاده می‌کنند:
- **Bale:** `Bale.WebApp.initData`، ارسال رشته خام به Backend، ساخت data-check-string از فیلدهای مرتب‌شده و اعتبارسنجی `hash` با HMAC-SHA-256؛ بررسی تازگی `auth_date` نیز توصیه شده است.
- **Telegram:** `Telegram.WebApp.initData` و همان روش HMAC برای Backend خود ربات. امضای Ed25519 در بخش «third-party validation» مسیر جداگانه‌ای است و برای اعتبارسنجی مستقیم توسط Backend خود ربات لازم نیست.
- هر پلتفرم باید با **توکن محرمانه مستقل خودش** اعتبارسنجی شود؛ نام پلتفرم ارسالی کلاینت به‌تنهایی معتبر نیست و فقط تعیین می‌کند کدام کلید سرور برای بررسی استفاده شود.

منابع رسمی:
- Bale Mini Apps: https://docs.bale.ai/miniapp (بخش‌های WebApp و اعتبارسنجی داده‌های دریافتی، خطوط ۸۱–۹۱ و ۲۴۵–۲۶۰)
- Telegram Mini Apps: https://core.telegram.org/bots/webapps (بخش Initializing Mini Apps و Validating data received via the Mini App)

### پیاده‌سازی محدود انجام‌شده

- فایل `workers/assistant-api/src/platformAuth.js` افزوده شد.
- تابع `verifyMiniAppInitData` برای Telegram و Bale:
  - ورودی را از نظر اندازه محدود می‌کند؛
  - فیلدهای تکراری را رد می‌کند؛
  - وجود `hash`، `auth_date` و `user.id` معتبر را بررسی می‌کند؛
  - تازگی ۵ دقیقه‌ای و حداکثر اختلاف آینده ۳۰ ثانیه را فعلاً اعمال می‌کند؛
  - HMAC را با Web Crypto و مقایسه امن `crypto.subtle.verify` می‌سنجد؛
  - فقط `valid`, `platform`, `authDate` برمی‌گرداند و شناسه/نام/پروفایل کاربر یا متن خام را بازنمی‌گرداند.
- متغیرهای secret مورد انتظار در آینده: `TELEGRAM_BOT_TOKEN` و `BALE_BOT_TOKEN`؛ هیچ‌کدام در Cloudflare تنظیم نشده‌اند و هیچ توکنی در مخزن ثبت نشده است.
- آزمون‌های `tests/platformAuth.test.js` برای امضای معتبر هر دو پلتفرم، کلید اشتباه، دستکاری داده، انقضا، زمان آینده، فیلد تکراری، ورودی بزرگ/ناقص، secret مفقود و user نامعتبر اضافه شده‌اند.

### محدودیت صریح این مرحله

این کد فقط **primitive اعتبارسنجی** است؛ هنوز به Worker route یا frontend متصل نشده است. هنوز:
- هیچ session token صادر نمی‌شود؛
- replay protection/nonce storage پیاده‌سازی نشده است؛
- `initData` از SDK در frontend خوانده یا ارسال نمی‌شود؛
- هیچ consent یا متن مکالمه ارسال نمی‌شود؛
- endpoint `/v1/assistant/turn` همچنان 503 و fail-closed است.

TTL پنج‌دقیقه‌ای فعلاً یک مقدار محافظه‌کارانه برای آزمون است، نه تصمیم UX نهایی؛ چون `auth_date` زمان بازشدن Mini App است، باید پیش از اتصال frontend سناریوی کاربری که اپ را مدت بیشتری باز نگه می‌دارد و راهکار refresh/replay protection بررسی شود. اعتبار امضای پلتفرم به‌هیچ‌وجه معادل رضایت پردازش ابری نیست.

**وضعیت:** primitive کدنویسی شده؛ عبور از CI و بازبینی نهایی هنوز لازم است؛ اتصال runtime و تست واقعی Telegram/Bale انجام نشده است.

## ۱۳. طراحی پیشنهادی ضدبازپخش، نشست و محدودسازی (بازبینی 2026-11-04)

این بخش تصمیم معماری برای پیاده‌سازی بعدی است؛ هنوز هیچ کد اجرایی، binding یا namespace ساخته نشده است.

### ۱۳.۱ جریان bootstrap
1. کلاینت فقط هنگام ورود کاربر به دستیار، `platform` و `initData` خام را به `POST /v1/session/bootstrap` می‌فرستد؛ هیچ پیام مکالمه‌ای در این درخواست وجود ندارد.
2. Worker اندازه و schema درخواست را محدود می‌کند، پلتفرم را allowlist می‌کند و HMAC را با bot token همان پلتفرم اعتبارسنجی می‌کند.
3. پس از موفقیت HMAC و بررسی تازگی `auth_date`، Worker یک fingerprint keyed (HMAC سمت سرور از پلتفرم و داده امضاشده) می‌سازد؛ نه raw initData و نه شناسه کاربر.
4. Worker عملیات اتمیک `consumeOnce` را در SQLite Durable Object مناسب shard اجرا می‌کند. کلید یکتا مانع مصرف دوباره همان fingerprint می‌شود. فقط درخواست برنده مجاز به ادامه است.
5. فقط پس از موفقیت ذخیره پایدار، Worker bearer session امضاشده HMAC-SHA-256 صادر می‌کند. اگر binding غایب، storage خراب یا Durable Object در دسترس نباشد، bootstrap fail-closed می‌شود و token صادر نمی‌شود.

### ۱۳.۲ ذخیره replay و پاک‌سازی
- یک کلاس SQLite-backed Durable Object با شناسه‌های shard‌شده بر اساس prefix fingerprint استفاده شود تا یک object مرکزی bottleneck نشود؛ یک fingerprint مشخص همیشه به همان shard برسد.
- جدول replay فقط fingerprint keyed و زمان انقضای مجاز را نگه می‌دارد؛ هیچ raw initData، hash امضای خام، user ID، پرونده یا متن گفتگو ذخیره نمی‌شود.
- قید `PRIMARY KEY` و درج اتمیک، رقابت دو درخواست هم‌زمان را حل می‌کند: فقط یکی درج موفق دارد.
- marker باید تا پایان آخرین لحظه‌ای که verifier ممکن است همان initData را معتبر بداند باقی بماند؛ زمان حذف بر اساس `auth_date + MAX_AUTH_AGE + MAX_FUTURE_SKEW` محاسبه می‌شود، نه صرفاً چند دقیقه پس از اولین درخواست.
- برای پاک‌سازی قطعی از یک Alarm برای هر shard استفاده شود: نزدیک‌ترین expiry زمان alarm است؛ handler رکوردهای منقضی را batch-delete می‌کند و alarm بعدی را برای نزدیک‌ترین expiry باقی‌مانده تنظیم می‌کند. خطای پاک‌سازی باید retry و قابل پایش باشد.
- shard count، batch size و تعداد عملیات باید با آزمون بار و سهمیه‌های واقعی تعیین شوند؛ مقدار اولیه در این سند قطعی نیست.

### ۱۳.۳ نشست امضاشده
- claimهای مجاز حداقلی: `iss`, `aud`, `iat`, `exp`, `jti`, `scope` و شناسه تصادفی نشست `sid`.
- `sid` و `jti` از مولد رمزنگاری امن تولید شوند؛ token با HMAC-SHA-256 و secret مستقل از bot tokenها امضا شود.
- هیچ user ID، شناسه پرونده، نام، شماره تماس، مشخصات پزشکی یا متن گفتگو داخل token قرار نگیرد.
- scope فقط `assistant:turn` باشد؛ عمر اولیه حداکثر ۱۰ دقیقه (پیشنهادی، نه نهایی). token فقط در حافظه runtime کلاینت نگهداری شود و هرگز در URL، query string یا localStorage دائمی قرار نگیرد.
- هر درخواست turn باید امضا، issuer، audience، زمان، scope و ساختار claimها را بررسی کند.
- در نسخه اول refresh token صادر نشود. تمدید نشست فقط پس از bootstrap جدید با initData تازه و یک‌بارمصرف مجاز است؛ بنابراین انقضای نشست ممکن است کاربر را ملزم به بستن و بازکردن Mini App کند. این هزینه UX باید در تست واقعی اندازه‌گیری شود.
- revocation فوری و withdrawal رضایت به state سروری جداگانه نیاز دارند و پیش‌نیاز فعال‌سازی پردازش ابری هستند؛ token کوتاه‌عمر به‌تنهایی جایگزین withdrawal نیست.

### ۱۳.۴ محدودسازی نرخ
- bootstrap و turn هر دو در سمت سرور محدود شوند؛ محدودیت UI یا CORS کنترل سوءاستفاده نیست.
- محدودیت اولیه turn بر مبنای HMAC مستعارشده `sid` و پنجره زمانی اتمیک در Durable Object باشد؛ سقف ۲۰ درخواست در ۱۰ دقیقه فقط نقطه شروع آزمون است، نه سقف نهایی محصول.
- bootstrap باید پیش از عملیات رمزنگاری سنگین، محدودیت شبکه‌ای داشته باشد. اگر از `CF-Connecting-IP` استفاده شود، فقط مقدار تأییدشده در مرز Cloudflare خوانده و بلافاصله با secret سرور HMAC شود؛ IP خام هرگز ذخیره یا log نشود. سقف شبکه نباید کاربران پشت NAT را بی‌دلیل محروم کند.
- در فاز پیاده‌سازی هزینه تعداد RPCهای DO در هر درخواست محاسبه شود. هر RPC session/HTTP request/alarm invocation یک DO request قابل صورتحساب است؛ free tier فعلی ۱۰۰٬۰۰۰ request در روز است و عبور از سقف رایگان می‌تواند عملیات همان نوع را متوقف کند.
- در خطای DO، رسیدن به سهمیه، شکست storage یا ابهام در شمارنده، مسیر حساس باید fail-closed باشد.

### ۱۳.۵ تصمیم‌های باز و شروط ورود به کدنویسی
- TTL پنج‌دقیقه‌ای فعلی `auth_date` هنوز provisional است. افزایش آن بدون اندازه‌گیری UX و threat review مجاز نیست؛ تست واقعی باید فاصله زمانی بازشدن Mini App تا ورود به دستیار را نشان دهد.
- روش بارگذاری SDK Bale هنوز به دلیل توصیه رسمی بارگذاری در ابتدای `<head>` و تفاوت با lazy-load فعلی حل نشده است.
- کلیدهای HMAC باید جدا باشند: bot token پلتفرم برای verify، session signing secret برای token، و replay-fingerprint secret برای pseudonymous storage. هیچ‌کدام در Git یا frontend قرار نمی‌گیرند.
- قبل از افزودن migration/binding باید نوع پلن حساب، namespace/migration و هزینه/سهمیه در داشبورد به‌صورت read-only تأیید شود. ساخت namespace یا deploy بدون اجازه صریح ممنوع است.
- ابتدا کلاس DO و منطق replay در تست‌های محلی/CI با شبیه‌سازی concurrency، duplicate، expiry، alarm cleanup و storage failure آزموده شوند. سپس route bootstrap فقط پس از تأیید انسانی برای آزمون میزبان اضافه شود.
- `/v1/assistant/turn` تا تکمیل رضایت، privacy, safety, schema و provider review همچنان 503 باقی می‌ماند.
